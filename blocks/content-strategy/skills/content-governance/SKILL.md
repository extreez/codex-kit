# Governance контента

Не про то, что писать (см. `content-strategy`) и не про то, как
писать (см. `content-production`) — про то, как контент движется от
идеи до публикации так, чтобы ничего не терялось и не публиковалось
без проверки.

## Жизненный цикл

```
SIGNAL → CANDIDATE → DRAFT → REVIEW → APPROVED_FOR_PUBLISH
       → PUBLISHED → READBACK → LEARNING
```

| Стадия | Что происходит | Кто отвечает |
|---|---|---|
| **SIGNAL** | Сырой сигнал — идея, тренд, вопрос от клиента, конкурентная новость. Ещё не решено, писать ли об этом. | Кто угодно в команде |
| **CANDIDATE** | Сигнал прошёл приоритизацию (`content-strategy`), стал строкой в бэклоге с оценкой. | Владелец контент-стратегии |
| **DRAFT** | Идёт написание (`content-production`, режимы Research&Brief → Draft). | Автор |
| **REVIEW** | Черновик готов, идёт проверка — редактура (`copy-editing`), опционально `expert-panel-review`. | Редактор |
| **APPROVED_FOR_PUBLISH** | Прошёл проверку, ждёт публикации (может быть запланирован на дату в календаре). | Редактор/владелец |
| **PUBLISHED** | Опубликовано, доступно аудитории. | — |
| **READBACK** | Замер результата после публикации — трафик, вовлечённость, конверсия (см. `metrics/analytics-readback`). | Владелец аналитики |
| **LEARNING** | Вывод зафиксирован — сработало/не сработало и почему, идёт в плейбук или влияет на будущую приоритизацию. | Владелец контент-стратегии |

## Правила одобрения

- **Ни один материал не переходит в PUBLISHED без явного одобрения**
  на стадии REVIEW от роли, отличной от автора (даже если это
  формальность в маленькой команде — фиксация ответственности).
- **READBACK обязателен для столпового/флагманского контента**,
  опционален для рядовых публикаций с низкой ставкой — правило
  соразмерности усилия важности материала.
- **Возврат назад по циклу разрешён** — REVIEW может вернуть материал
  в DRAFT, READBACK может показать, что нужна ревизия уже
  опубликованного (обновить, не считать цикл закрытым намертво).

## Минимальный трекер (без конкретного инструмента)

Одна таблица/доска с колонками = стадии цикла. Обязательные поля на
карточку: тема, целевой ключ/аудитория, автор, дата входа в текущую
стадию, ссылка на бриф (если есть), для READBACK — baseline/candidate
метрики и решение (см. `metrics/analytics-readback` за форматом).

Если ставится блок `content-loop` (автоматика продвижения по стадиям
+ Stop-гейт на непровалидированную публикацию) — трекер должен лежать
конкретно в `docs/marketing/content-pipeline.md`, формат:

```markdown
| Тема | Stage | Дата входа в стадию | Дата публикации | Readback |
|---|---|---|---|---|
```

`content-loop` читает только эти пять колонок построчным парсером (не
полноценный markdown-парсер) — лишние колонки не мешают, но порядок и
названия этих пяти менять нельзя, иначе Stop-гейт перестанет находить
зависшие публикации.

## Частые ошибки

- Стадии DRAFT/REVIEW сливаются в одну — автор одобряет сам себя,
  теряется независимая проверка.
- READBACK пропускается систематически — весь контент считается
  «успешным», потому что никто не проверял после публикации.
- Нет явного возврата назад — материал, не прошедший REVIEW, тихо
  зависает вместо явного статуса «на доработке».

## Вопросы для уточнения задачи

1. Это настройка процесса с нуля или ревизия существующего?
2. Кто в команде будет играть роль независимого REVIEW — есть ли
   отдельный редактор, или это тот же человек, что и автор?
3. Насколько строгий READBACK нужен — для всего контента или только
   для столпового?
