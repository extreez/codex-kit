# dev-build

Router. `научи` — режим объяснения. Пусто или что угодно ещё — обычная работа
ниже.

Не пишет код сам и не заменяет обычную дисциплину «правка + проверяемый чек»
(та уже встроена в стиль ответов). Этот блок нужен, когда работа крупнее одной
правки: спека или тикет, которые не влезают в одну сессию без разбивки.

## Режим «научи»

Пять строк по-русски, без терминов без расшифровки, плюс одна команда
попробовать прямо сейчас:

```
Спека — это описание того, что должно получиться, до того как начали писать код.
dev-build режет её на срезы: срез — маленький кусок, после которого что-то
реально заработало и это можно проверить командой (тест прошёл, файл появился).
Не «слой» типа «сначала база, потом бэкенд, потом фронт» — а сквозной путь:
одна кнопка, которая реально нажимается и что-то делает, от начала до конца.
Дальше срезы идут по одному через loop-build: пока текущий не зелёный —
следующий не начинается.
Попробовать: опиши одну фичу, и я нарежу её на срезы прямо сейчас.
```

## Когда не нужен

Одна правка, один файл, один чек — просто делай, без этого блока. Блок только
для работы, которая иначе превратится в один гигантский необратимый диф.

## Порядок

### Шаг 1. Прочитать спеку целиком

Не резать на срезы, не поняв весь объём. Отметь, что в спеке неоднозначно —
спроси один раз, не гадай.

### Шаг 2. Нарезать на срезы

Срез — минимальный кусок, после которого система в рабочем состоянии и есть
факт, что он работает. Не «слой», не «модуль» — сквозной путь через все слои,
которые он трогает.

Каждый срез:
| Поле | Что писать |
|---|---|
| Название | что стало работать после среза |
| Красный тест | что должно упасть до реализации |
| Зелёный чек | команда, которая подтвердит срез закрытым |
| Зависит от | какой срез должен быть закрытым раньше |

Срезов много и они мелкие — нормально. Срез, который нельзя проверить одной
командой, режь дальше.

### Шаг 3. Записать срезы в файл

Пиши список в `docs/dev/slices.json` — не держи только в переписке. Формат,
массив объектов:

```json
[
  {
    "id": "S1",
    "name": "что стало работать",
    "red_check": "команда/тест, который должен упасть до реализации",
    "green_check": "команда, которая подтвердит срез закрытым",
    "depends_on": [],
    "status": "pending"
  }
]
```

`status`: `pending` (не начат), `in_progress`, `done`. Этот файл читает
`dev-loop` — цикл узнаёт, где остановился, из файла, не с ваших слов и не
заново глазами по коду.

Список срезов уже существует (второй заход на ту же спеку) — не начинай с
нуля: дочитай статусы, продолжай с первого `pending`.

### Шаг 4. Отдать в loop-build

Список срезов — это не то, что выполняет сам dev-build. Передай его в
`loop-build` (Skill tool) как последовательность: один срез — один проход,
чек следующего среза не запускается, пока не зелёный текущий. Каждый проход
обновляет `status` в `docs/dev/slices.json`.

### Шаг 5. Красный-зелёный на каждом срезе

Если ведёшь срез сам, без loop-build: сначала тест, который падает по нужной
причине (не по опечатке), потом минимальный код, чтобы тест прошёл. Не рефактори
и не добавляй впрок — это будет уже следующий срез. Закрыл срез — обнови его
`status` на `done` в файле.

## Соседи

Прогнать срезы по кругу — `loop-build` или свой `dev-loop` (тот же файл
срезов, плюс гейт на выходе из сессии). Диф проверить — `/code-review`.
Одна правка без спеки — просто делай, без этого блока.
