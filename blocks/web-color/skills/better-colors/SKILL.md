# Цвет

Цветовая система — это небольшой набор рамп, названных по роли и
проверенных на тех фонах, на которых они реально рендерятся. Большинство
цветовых багов — баги системы: значение, подобранное изолированно, токен,
позаимствованный потому что «на вид подошёл», пара, которую никто не
измерил.

Никогда не сообщать значение контраста, которое не измерено, и никогда не
прикидывать цвет, который можно посчитать. Цвет — одна из немногих тем
интерфейса с точным ответом, поэтому давать точный ответ.

## Работай в нотации проекта

Переиспользуй токены и нотацию проекта. Второе представление, добавленное
ради одного значения, усложняет чтение палитры. Последовательный hex лучше,
чем hex с разбросанными по нему `oklch()`.

Для новой системы `oklch()` — лучший выбор по умолчанию, потому что его
числа ведут себя ровно так, как описывают правила рампы ниже. Везде
остальное — цветовая библиотека выдаёт ту же рампу в нотации проекта
([color-formats.md](color-formats.md)).

## Система — это рампы, не цвета

Одна нейтральная рампа, одна акцентная рампа и только те статусные рампы,
которые продукт реально рендерит. `warning`-рампа, которую никто не
импортирует — это обслуживание нуля пикселей. Второй акцентный оттенок
оправдан только тогда, когда два элемента обязаны различаться с одного
взгляда.

## У каждого шага есть работа

Рампа — не градиент, из которого выбирают на глаз. Каждый шаг существует
потому, что его требует роль: фон страницы, hover компонента, граница,
сплошная заливка, текст. Не генерировать шаг, который не потребляет ни
одна роль. И Tailwind-конвенция `50`-`950`, и Radix `1`-`12` отображаются
на эти роли ([palette-structure.md](palette-structure.md)).

## Примитивы называй по оттенку, семантику — по роли

Примитивы называют значение (`--blue-500`) и никогда не применяются
напрямую в компоненте. Семантические токены называют работу
(`--color-text-secondary`), указывают на примитив и являются единственным
уровнем, на который ссылаются компоненты.

Именно этот шов делает возможной темизацию. Без него тёмная тема означает
аудит каждого использования, чтобы понять, кто имел в виду «акцент», а кто
просто хотел синий ([token-naming.md](token-naming.md)).

## Используй токен только в его роли

Никогда не занимай токен потому что его значение сегодня подходит.
Разделитель, использованный как цвет текста, работает — пока границы не
станут светлее, и тогда текст посветлеет вместе с ними. Если у роли нет
токена — добавь токен.

## Держи оттенок постоянным вдоль рампы

Четыре свойства определяют правильно построенную рампу:

- Шаги равномерны по *воспринимаемой* светлоте, не по тому, что формат
  называет светлотой.
- Оттенок остаётся постоянным от начала до конца.
- Насыщенность пиковая в середине рампы и спадает на обоих концах.
- Шаги плотнее на светлом конце, чем на тёмном.

Оба конца останавливаются, не доходя до чистого чёрного и белого — они не
способны нести оттенок вообще. Использовать цветовую библиотеку, а не
подбирать на глаз ([palette-generation.md](palette-generation.md)).

## Один цвет — одно значение

Использовать цвет для одной цели во всём интерфейсе, считая любые оттенки
в пределах `15°` одним цветом. Если акцент означает «интерактивный», этот
же оттенок на статичном тексте говорит пользователю кликнуть туда, где
кликать нечего, а интерактивный элемент, отрисованный нейтральным цветом,
вводит в заблуждение так же сильно. Цвет никогда не единственный носитель
смысла — это забота `web-a11y-code`.

## Заливай ровно одно действие на экран

Когда заливка цветом кодирует главный акцент — эту заливку получает одно
главное действие, остальные остаются нейтральными. Класть цвет на фон, не
на подпись: заполненная кнопка читается как главная через всю комнату,
акцентный текст на нейтральной кнопке читается как ссылка.

Несколько цветных фонов — нормально, когда они кодируют разные состояния
или категории, а не конкурируют как равные.

## Измеряй отрендеренную пару, потом сообщай

Измерять цвет переднего плана против фона, на котором он реально
рендерится, не против фона страницы. Когда пара проваливается — сообщать
саму пару, измеренное значение и порог, который она не прошла, и оставить
цвета как есть. Это дизайн-решение. Менять только по запросу, и
перемерить после ([contrast.md](contrast.md)).

## Выбирай пространство интерполяции градиента

Пространство — это внешний вид, не критерий правильности.

- **`in oklab`** — лучший выбор по умолчанию: равномерная яркость, без
  сюрпризов с оттенком.
- **`in oklch`** идёт по кругу цветового круга, а не через середину,
  оставаясь насыщенным и проходя через каждый оттенок между стопами.
  Использовать, когда двухцветный градиент сереет в середине.
- **sRGB по умолчанию** темнит и приглушает середину. Это то, что уже есть
  в большинстве интерфейсов, потому что это получается само, без
  дополнительных действий.

Подробнее — [color-usage.md](color-usage.md).

## Перед тем как закончить

| Ошибка | Фикс |
| --- | --- |
| Сырое значение там, где у проекта есть токен | Переиспользовать или добавить токен роли, в нотации проекта |
| Изолированный `oklch()`, вставленный в hex-кодовую базу | Сохранить установленную нотацию, если миграция не входит в задачу |
| Примитив вроде `--blue-500` использован напрямую в компоненте | Указать на него семантическим токеном |
| Токен назван по внешнему виду (`--color-blue-button`) или по первому использованию (`--color-sidebar-gray`) | Назвать по роли: `--color-accent-solid`, `--color-bg-surface` |
| `--color-primary` значит бренд, а `--color-text-primary` значит основной текст | Зарезервировать `accent` за брендом; пусть `primary` значит «самый заметный в своей группе» |
| Семантический токен использован вне своей роли (разделитель как цвет текста) | Добавить токен для недостающей роли; никогда не занимать по значению |
| Рампа построена варьированием HSL-светлоты | Пересобрать по воспринимаемой светлоте с постоянным оттенком |
| Рампа равномерно распределена по всему диапазону | Сжать светлый конец, чтобы `50` и `100` читались как две разные поверхности |
| Одно и то же число насыщенности переиспользовано между оттенками | Соответствовать доле от максимума каждого оттенка, не сырому значению |
| Статусный оттенок сталкивается с оттенком акцента | Сдвинуть его, пока destructive и primary не станут различимы рядом |
| Тёмная тема сделана механическим разворотом светлой палитры | Развернуть как отправную точку, затем снизить насыщенность, расширить тёмный конец и перепроверить каждую пару |
| `prefers-color-scheme` задаёт часть токенов, а `.dark`-класс — другую часть | Выбрать один механизм переключения и использовать его везде |
| Контраст чинится сменой оттенка | Менять светлоту — именно на этот канал реагирует контраст |
| P3-цвет без sRGB-фолбэка | Сначала объявить sRGB-значение, затем переопределить внутри `@media (color-gamut: p3)` |

## Формат отчёта

**Severity.** `HIGH` делает контент нечитаемым или назначает вводящий в
заблуждение семантический цвет. `MEDIUM` — заметный сбой темы, токена или
gamut. `LOW` — изолированная полировка.

**Верификация.** Без браузера: значения токенов, gamut каждого объявленного
цвета, наличие обоих тема-блоков и контраст, посчитанный по объявленной
паре токенов. С браузером: фон, реально отрендеренный за текстом, включая
прозрачность и любое изображение под ним, измеренный в обеих темах.
Проваленная пара сообщается, не перекрашивается. Каждую непроверенную
проверку помечать `Not verified`.

**Формат.** Группировать находки по нарушенному принципу, по убыванию
severity, одна строка на первопричину со всеми местами, где она
встречается:

| Severity | Место | До | После | Почему |
| --- | --- | --- | --- | --- |

`Место` — `path/to/file:line`. `Почему` называет принцип и последствие для
пользователя.

Закончить `Block`, если остался хоть один `HIGH`, иначе `Approve`, остальное
оставить в таблице как работу на потом. Никогда не `Approve` покрытие,
которое не проверял. Если нечего сообщить — «Нет действенных находок по
цвету» и отчёт верификации.

## Проверяемый результат (для /loop-build)

Ramp-шаги и контраст между ними численно проверяемы — `check_contrast.py`
(web-taste/gate-check) на все пары текст/фон рампы. Готово — когда чист.
Выбор самой палитры (гармония, вайб) — вердикт verifier-subagent.

## Несколько тем/брендов сразу — распараллелить

Строишь палитру сразу для нескольких тем (light/dark/brand-variant) —
subagent на тему, независимо, контраст проверяется в каждой отдельно.

## Synthesized palette and theme rules

When starting from one or two brand colors, derive the ramp in OKLCH, then map
it to semantic roles rather than using raw values in components. Generate
interactive states from the base role, keep status colors few and unambiguous,
and validate contrast in every theme. A dark theme changes surface hierarchy;
it is not a simple inversion of the light palette.
