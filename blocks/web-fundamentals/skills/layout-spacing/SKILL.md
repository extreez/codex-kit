# Layout & Spacing

Положение, отступ и выравнивание несут иерархию раньше, чем прочитано
слово. Этот скилл строит эту структуру и стресс-тестирует её: измени
размер, переведи, отзеркаль под RTL.

Пиши каждый фикс в стилевой системе проекта. Числа ниже — отправная точка
для интерфейсов без сложившейся density-системы; там, где она есть,
использовать её как есть, не подставлять похожий на вид аналог. Сохранять
осознанный платформенный chrome, компактные профессиональные инструменты и
токены проекта там, где они проходят стресс-тесты ниже.

## Словарь: типы грида и density-режимы

Прежде чем численные правила ниже — базовый словарь для описания layout.

**Типы грида:**
- **Column grid** — равные колонки для общего layout
- **Modular grid** — колонки + строки, образующие модули
- **Baseline grid** — вертикальный ритм выравнивания (4px или 8px)
- **Compound grid** — перекрывающиеся гриды для сложных layout

**Анатомия грида:** колонки (обычно 4 на мобильном, 8 на планшете, 12 на
десктопе), gutters — пространство между колонками (16/24/32px), margins —
внешние отступы страницы (16px мобильный, 24-48px десктоп), breakpoints —
точки, где layout адаптируется.

**Density-режимы** (модификатор поверх любой спейсинг-шкалы):
- **Compact** — уменьшить отступы на один шаг (для data-heavy view)
- **Comfortable** — дефолтные отступы
- **Spacious** — увеличить отступы на один шаг (для reading-focused view)

Дальше — точные числа и код для реализации этого словаря.

## Группируй пространством, не линиями

Пространство группирует в первую очередь, фоновые формы — во вторую,
разделительные линии — в последнюю, и только там, где пространство само не
может нести структуру. Отступ между группами должен быть минимум в 2 раза
больше отступа внутри группы (`8px` внутригрупповой → `16px`+
межгрупповой), иначе группировка читается как шум. Выравнивание по краям и
порядок по важности — в [grouping-and-alignment.md](grouping-and-alignment.md).

## Держи контролы отличимыми от контента

У каждого интерактивного элемента должна быть фоновая форма, граница или
последовательная зона размещения. Контрол, стилизованный как статичный
текст рядом с ним, не читается как контрол.

## Выравнивай по общим краям

Выбери края выравнивания и придерживайся их; каждый случайный край читается
как шум. Используй один шаг отступа проекта на уровень подчинения, `16px`
— полезный дефолт.

Используй логические свойства для направленно-зависимого layout:
`padding-inline-start`, `margin-inline-end`. Физические left/right
оставляй только для действительно физической геометрии.

## Упорядочивай по важности

Самый важный контент — ближе к верху и ведущему краю. Порядок чтения течёт
сверху вниз, от ведущего края к последующему. Думай в терминах leading/
trailing, не left/right.

## Намекай на скрытый контент

Progressive disclosure нуждается в видимом аффордансе. Используй
сложившийся в проекте сигнал, или дай следующему элементу «выглянуть» на
`16-32px` за край скролла, или покажи disclosure-контрол. Контент, скрытый
без сигнала, всё равно что не существует.

## Пространство для дыхания между таргетами

Без сложившейся density-системы — начни с `12px` между соседними
контролами с рамкой/заливкой и `24px` вокруг безрамочных
текстовых/иконочных. Компактные layout могут использовать меньше, пока
hit-area (`web-a11y-code`, когда появится) не перекрываются, а контролы
остаются отличимыми. Margins и breakpoint-рецепты — в
[spacing-and-adaptivity.md](spacing-and-adaptivity.md).

## Отступай кнопки от краёв

В content-layout держи full-width кнопки внутри layout margins с видимым
радиусом, начиная около `16px` inline на мобильном. Edge-to-edge действия
работают, когда следуют сложившемуся платформенному chrome, учитывают safe
area и остаются отличимыми от системного UI.

## Контент течёт до края, контролы плавают

Фоны и медиа простираются до краёв viewport. Контролы и текст остаются
внутри layout margins и safe area (`env(safe-area-inset-*)`). Sticky-chrome
плавает над слоем контента, не блокирует его.

## Держи структуру, пока не сломается

Breakpoints идут от контента, не от пресетов устройств. Держи развёрнутый
layout, пока он реально помещается, и схлопывай поздно. Предпочитай
container queries для компонентной адаптации, тестируй сначала самый
маленький и самый большой размер.

## Планируй рост и обрезание

Переведённые строки растут, и короткие растут пропорционально сильнее, так
что однословный лейбл кнопки — самое рискованное на экране. Не задавай
фиксированную ширину/высоту текстовому контейнеру, дай строкам
переноситься. Тестируй с псевдо-локализацией и одной реальной локалью,
вместо того чтобы закладывать процент на глаз.

Никогда не помещай критичное действие туда, где его обрежет ресайз или
скролл. Держи его в обычном потоке или в стабильном chrome, подходящем
продукту.

## Перед тем как закончить

| Ошибка | Фикс |
|---|---|
| `margin-left`/`padding-right` в локализуемом layout | `margin-inline-start`/`padding-inline-end` |
| Кнопка content-layout касается края viewport | Отступить внутрь margins проекта; сохранить намеренный платформенный chrome |
| Breakpoints на 768/1024, потому что это дефолты | Ломать там, где контент реально перестаёт помещаться |
| Текстовый контейнер фиксированной ширины под один язык | `max-width` и перенос; тестировать псевдо-локализацией |
| Основное действие в обрезаемом низу панели | Sticky-позиционирование или стабильный chrome с safe-area padding |

## Формат отчёта

**Severity.** `HIGH` блокирует контент или действие на поддерживаемом
viewport. `MEDIUM` вредит иерархии, порядку чтения или адаптивности. `LOW`
— изолированная полировка выравнивания/отступа.

**Верификация.** Без браузера: логические свойства вместо физических,
container/media queries против списка поддерживаемых viewport, DOM-порядок
против задуманного порядка чтения. С браузером: каждая поддерживаемая
ширина, зум 200%, RTL-зеркало. Каждую непроверенную проверку помечать
`Not verified`.

**Формат.** Группировать находки по нарушенному принципу, по убыванию
severity, одна строка на первопричину со всеми местами:

| Severity | Место | До | После | Почему |
|---|---|---|---|---|

`Место` — `path/to/file:line`. `Почему` называет принцип и последствие для
пользователя.

Закончить `Block`, если остался хоть один `HIGH`, иначе `Approve`, остальное
оставить в таблице как работу на потом. Никогда не `Approve` покрытие,
которое не проверял. Если нечего сообщить — «Нет действенных находок по
layout» и отчёт верификации.

## Synthesized interface rules

Use this skill as the home for structure-level decisions formerly spread across
narrow UI skills: information architecture, Gestalt grouping, layout choice,
responsive behavior, density, scope signaling, tabs, sticky elements, scroll
containers, data views, and guided flows. Decide the user's task and hierarchy
first, then choose the smallest layout that supports it. Mobile is an
interaction change, not a scaled desktop layout. Avoid nested scroll regions
and make scope and consequences visible before an action.
