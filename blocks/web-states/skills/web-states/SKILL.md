# UI State Expander

Хороший интерфейс — не один кадр, это система состояний, меняющихся во
времени, при неопределённости, при неполных данных и технических сбоях.
Задача — сделать эти состояния видимыми, явными и готовыми к реализации.
Если состояние не спроектировано, инженер придумает его на ходу — так
продукт обрастает странными окаменелостями.

## Шаг 0: получить реальный дизайн

Если дана ссылка на Figma - использовать Figma-коннектор (`figma-mcp`) и
забрать фрейм: существующие варианты и свойства компонента показывают,
какие состояния уже спроектированы, чтобы сфокусироваться на том, чего
*не хватает*. По одному скриншоту - озвучить допущения. Без того и
другого - сначала попросить дизайн или описание UI.

## Базовые принципы

1. **Экран - конечный автомат, не постер.** Happy path - одно условие
   среди многих.
2. **Крайние случаи - нормальные случаи.** Длинный текст, нулевые
   значения, частичные данные, ошибки - ожидаемая погода в проде, не
   исключение.
3. **Состояния взаимодействия - то, как интерфейс отвечает.** Hover,
   focus, pressed, disabled, loading - функциональны, не декоративны.
4. **Переходы важны.** Loading→контент, saving→success, failure→retry
   должны ощущаться связно, не как резкая склейка.
5. **Ясность состояния важнее визуального совершенства.** Простое
   состояние, понятное пользователю, лучше красивого, оставляющего в
   недоумении.

## Уточнить, прежде чем гадать

Спросить только необходимый минимум: основная задача, какие данные могут
не загрузиться или отсутствовать, из каких состояний пользователь должен
уметь восстановиться, это компонент/страница/флоу, и есть ли бизнес-правила
для пустых/ошибочных состояний. Если это уже видно из контекста - не
переспрашивать.

## Рабочий процесс

### 1. Определить объект

Страница, компонент, форма, список, таблица, модалка, drawer, wizard, или
целый флоу - это определяет, какие семейства состояний применимы.

### 2. Инвентаризировать состояния

Пройти по шести семействам ниже. Не каждое состояние применимо к каждому
UI - включать релевантное, и объяснять исключение, если оно неочевидно.

- **Состояния данных** - loading, изначально пусто, пусто после
  фильтрации, заполнено, частичные данные, нет доступа, нет соединения,
  устарело, оптимистичное обновление, неудачный fetch, успех/неудача
  повтора.
- **Состояния взаимодействия** - default, hover, focus, pressed, disabled,
  selected, развёрнуто/свёрнуто, перетаскивается, в процессе, завершено,
  отклонено.
- **Состояния формы** - placeholder, заполнено, редактируется, валидно,
  невалидно, обязательное не заполнено, автозаполнено, только чтение,
  отправляется, отправлено, сохранение не удалось.
- **Состояния контента** - короткий/длинный контент, пустой текст, очень
  большие/маленькие числа, null-значения, усечение, переполняющиеся
  лейблы, расширение текста при локализации.
- **Системные состояния** - доступ запрещён, не найдено, таймаут, ошибка
  сервера, офлайн, rate limit, техобслуживание, сессия истекла.
- **Состояния восстановления** - повтор, отмена, восстановление,
  черновик сохранён, переподключение, fallback-контент. Восстановление -
  то, что отличает устойчивый продукт от тупика.

### 3. Стресс-тест

Что происходит, когда текст становится длинным, данные отсутствуют,
значения нулевые, списки огромны, действия недоступны, соединение
обрывается, или пользователь обновляет страницу посреди задачи?

### 4. Отобразить переходы

Определить, как UI движется между состояниями (loading→контент,
editing→saving→success, failure→retry, empty→первое действие,
filtered-empty→сброс фильтров). Неопределённые переходы - то место, где
реализация расходится с задумкой.

### 5. Выдать готовое к реализации руководство

Варианты компонента, имена состояний, условия срабатывания, fallback-
поведение, требования к копирайту, правила взаимодействия, визуальные
изменения.

## Руководство по конкретным состояниям

- **Loading** - не просто спиннер. Skeleton, когда важна структура,
  спиннер, когда важен только факт активности, progress, когда важна
  длительность. Решить между inline-занятостью, полноэкранным блокером и
  отложенным раскрытием.
- **Empty**-состояниям нужен смысл. Первый запуск без данных, пусто после
  фильтра, ничего ещё не создано, и нет доступа - разные ситуации,
  нуждающиеся в разном тексте и разных следующих шагах. Один общий
  empty-state путает все четыре аудитории.
- **Ошибки** должны объяснять, что произошло, может ли пользователь это
  исправить, и что делать дальше. Конкретные сообщения лучше общего
  текста о сбое.
- **Disabled**-контролы обязаны сообщать *почему*, когда это не очевидно -
  безжизненный контрол без объяснения читается как баг. Иногда правильный
  фикс - состояние с подсказкой вместо disabled.
- **Success** должен ясно подтверждать результат, особенно для
  необратимых или высокорисковых действий.
- **Частичные данные** случаются постоянно (часть строк загрузилась, одна
  картинка не подгрузилась, опциональные поля отсутствуют) и не должны
  выглядеть сломанными.
- **Продуктовые гремлины на тест:** длинные имена и email, дробные числа,
  ноль, пустые массивы, ровно один элемент, тысячи элементов, дубликаты,
  неожиданная пунктуация.

## Формат вывода

Использовать эту структуру, если не попросили иначе:

1. **Сводка состояний** - что разворачивается и зачем.
2. **Инвентарь состояний** - полный набор нужных состояний, с триггером
   на каждое.
3. **Руководство по каждому состоянию** - как оно выглядит, что говорит,
   что позволяет.
4. **Логика переходов** - как пользователь движется между состояниями.
5. **Недостающие состояния** - состояния, отсутствующие в дизайне, но
   нужные (часто самая ценная часть вывода).
6. **Заметки по реализации** - варианты, именование, требования к
   копирайту, что инженерам нужно для чистой сборки.

Если пользователь хочет ревью - фокус на недостающих или недоспецифицированных
состояниях. Если генерацию - развернуть в полную модель состояний, готовую
к реализации без догадок.

## Доступность

Каждому интерактивному состоянию нужен доступ с клавиатуры и видимый
focus. Loading и success нуждаются в объявлениях для screen reader.
Статус не должен полагаться только на цвет. Проверить touch-таргеты,
обработку reduced-motion и порядок чтения в empty/partial-состояниях.
Состояние, работающее визуально, но проваливающее семантику, не считается
завершённым.

## Чего не делать

- Считать default-состояние единственным, использовать один общий
  empty-state на всё
- Скрывать причину disabled-контрола, когда она важна
- Оставлять переходы неопределёнными, забывать про partial и stale
  данные
- Останавливаться на визуале без поведения

## Проверяемый результат (для /loop-build)

Готово — когда все 6 семейств состояний (данные/взаимодействие/форма/
контент/система/восстановление) явно упомянуты для экрана хотя бы одним
пунктом, ни одно не помечено как "потом". Механически проверяемо:
итоговый список состояний содержит хотя бы один пункт на каждое из 6
слов-меток — можно сверить grep'ом по названиям семейств в выходном
файле, если список сохраняется в docs/.

## Несколько экранов сразу — распараллелить

Просят продумать состояния для многих экранов/компонентов разом (весь
флоу чекаута, все карточки в дашборде) — subagent на экран, каждый
разворачивает свои 6 семейств независимо. Общих данных между экранами
обычно нет; если есть переиспользуемый компонент (одна карточка на 5
экранах) — состояния этого компонента продумать один раз, не 5.
