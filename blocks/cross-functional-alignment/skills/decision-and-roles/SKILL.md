# Решения и роли

5 инструментов из `Owl-Listener/ux-pgm-skills`, обобщены от UX-команды
до любой кросс-функциональной группы. Файлы в `templates/` дословно на
английском, атрибуция в начале каждого.

## Какой инструмент когда

| Запрос пользователя | Файл | Что решает |
|---|---|---|
| «веди лог решений» | `templates/decision-log.md` | Что/почему/кто/когда/когда пересмотреть — чтобы решённое не обсуждали заново |
| «спроектируй процесс приёма заявок» | `templates/intake-process.md` | Одна точка входа, обязательные поля (проблема, не решение), фиксированный каданс триажа, SLA на ответ |
| «свяжи работу с OKR» | `templates/okr-alignment.md` | Каждый workstream → к какому Key Result он ведёт, найти «сиротскую» работу и непокрытые KR |
| «построй RACI» | `templates/raci-matrix.md` | Responsible/Accountable/Consulted/Informed — ровно один Accountable на строку |
| «зафиксируй working agreement» | `templates/working-agreement.md` | Каданс, хендоффы, decision rights, каналы связи, definition of ready/done между функциями |

## Как выбирать

`working-agreement` и `raci-matrix` решают смежные, но разные вопросы:
working agreement — про то, **как** команды работают вместе (ритуалы,
нормы), RACI — про то, **кто** решает и делает по конкретной строке
(деливерабл/решение). Использовать RACI только для действительно
критичных решений, не для каждой задачи — слишком много Consulted
замедляет всё.

`decision-log` и `okr-alignment` — оба про прозрачность, но разного
рода: лог фиксирует прошлые решения, okr-alignment проверяет, что
текущая работа вообще к чему-то ведёт. Использовать вместе на ревью
программы: сначала okr-alignment (что мы вообще делаем и зачем),
потом decision-log (почему мы решили делать это, а не другое).

Для дублирующей темы «связать OKR» на уровне генерации новых OKR (не
проверки существующих) — см. `product-execution/planning-docs/
brainstorm-okrs`, другая задача (создать, не проверить связь).
