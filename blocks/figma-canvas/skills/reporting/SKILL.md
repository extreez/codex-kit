# Reporting

Два скилла-рекапа. Оба read-only по умолчанию (Daily Report может
опционально создать один report-фрейм — с явного согласия пользователя).

## Режим 1 — Catch Me Up (быстрый рекап, только чат)

Когда пользователь запускает этот режим — дать ему чатовый рекап недавней
активности в файле. Никаких правок канваса, никаких новых узлов.

### Шаг 1 — Спросить период

Спросить: **"За какой период рассказать?"** Варианты: последние 24 часа /
последние 3 дня / последняя неделя / последний месяц / конкретная дата
(попросить ввести — например "15 июня" или "2026-06-15", конвертировать в
ISO 8601 на начало этого дня UTC). Вычислить cutoff-timestamp относительно
сегодняшней даты.

### Шаг 2 — Собрать данные комментариев

Вызвать `get_comments` по текущему файлу. Забрать достаточно страниц, чтобы
покрыть все комментарии с cutoff-даты (использовать курсор пагинации при
необходимости). Сначала `resolved: false` для открытых тредов, затем ещё
раз `resolved: true` для недавно закрытых — включать закрытые только если
их `resolvedAt` попадает в выбранное окно.

Извлечь: все root-комментарии (открывающие тред) после cutoff; все ответы
в тредах с активностью после cutoff; автора каждого комментария; таймстамп;
страницу, к которой прикреплён комментарий (если доступно); resolved или
ещё открыт.

### Шаг 3 — Осмотреть структуру файла для контекста

Через `evaluate_script` собрать лёгкие метаданные: имена и число страниц
(`figma.root.children.map(p => p.name)`), топ-уровневые имена фреймов на
каждой странице (до первых 10 на страницу). Это помогает контекстуализировать
расположение комментариев и даёт представление, какие области файла
существуют.

### Шаг 4 — Синтезировать и ответить в чате

Структурированный чатовый ответ — никакого вывода на канвас. Формат:

```
### Catch Me Up — [период, напр. "Past Week"]

**Contributors**
[кто оставлял комментарии в окне, по каким страницам/фреймам]

**Active Comment Threads**
[по каждому треду с активностью: открывающий комментарий, суть переписки
1-2 предложениями, open/resolved, если принято решение — отметить]
(если комментариев в окне нет — сказать явно)

**What Happened — Synopsis**
[3-5 предложений на основе комментариев и структуры файла о фокусе работы
за период; называть конкретные страницы/фреймы, если они повторяются]

**Key Decisions**
[выводы, аппрувы, изменения направления, явные решения из тредов; если
ничего конкретного не видно — "No explicit decisions found in comments
for this period."]
```

Тон разговорный и лаконичный — это брифинг, не документ. Не менять файл,
не создавать узлы.

## Режим 2 — Daily Report (отчёт для клиента/команды)

Суммирует дизайн-активность в текущем файле за выбранный период на языке,
понятном клиенту или коллеге — результаты и решения, не техшум.

### Шаг 1 — Спросить период и аудиторию

Прежде чем что-то собирать, задать два коротких вопроса (пропустить любой,
на который пользователь уже ответил в запросе):

1. **Период:** сегодня / эта неделя / этот месяц / произвольный диапазон
2. **Аудитория:** client-facing (простой язык, без внутреннего жаргона,
   фокус на прогрессе и решениях) или internal (можно с техдеталями,
   открытыми вопросами, TODO)

По умолчанию, если пользователь говорит "просто сделай": эта неделя,
client-facing.

### Шаг 2 — Собрать свидетельства

Собрать сигналы из всех доступных источников в файле:

1. **История версий / именованные чекпоинты** — заголовки и описания
   версий, сохранённых в периоде. Сильнейший сигнал намеренных вех.
2. **Страницы и фреймы** — просканировать структуру файла: новые страницы,
   новые топ-уровневые фреймы, фреймы с именами, намекающими на недавнюю
   работу (v2, -new, -final, -mobile, даты в именах), статус-маркеры (✅,
   🚧, WIP, Draft, Approved).
3. **Комментарии** — открытые и закрытые комментарии в периоде: вопросы,
   фидбек, подтверждённые решения. Отметить, кто где комментировал, где
   важно.
4. **Ветки (branches)** — активные или смёрженные, если файл их
   использует.
5. **История чата агента в этом файле** — задачи, которые агента просили
   выполнить в периоде (сгенерировал мобильные версии, применил рестайл,
   прогнал аудит).

Если источник недоступен (например история версий недоступна в этом
контексте) — не угадывать, отметить в конце отчёта: "Version history not
accessible — summary based on file structure, comments, and agent
activity."

### Шаг 3 — Синтезировать, не перечислять

Превратить сырые сигналы в смысл. Правила:

- Группировать по **воркстриму или странице**, не по источнику данных.
  "Homepage: hero redesigned, mobile version added, copy questions
  resolved" — не "Comments: 3, Frames: 5".
- Вести с **результатов**: что теперь готово, решено или доступно, чего не
  было раньше.
- Разделять **решения** (подтверждённые в комментариях/чекпоинтах) и
  **открытые вопросы** (нерешённые комментарии, WIP-маркеры).
- Квантифицировать только там, где это осмысленно (например "12 product
  page templates completed"), никогда не набивать счётчиками слоёв.
- Для client-facing отчётов: никаких имён слоёв, компонентного жаргона,
  внутренних сокращений. Переводить "detached instance fixed" в "visual
  inconsistency corrected".
- Никогда не изобретать активность. Если период выглядит тихим — сказать
  об этом честно и вместо этого суммировать текущее состояние.

### Шаг 4 — Сдать отчёт

**Чатовая сводка (всегда)** — формат:

```
**[Имя файла] — [Период] report**

**Done**
- результаты, сгруппированные по странице/воркстриму

**Decisions made**
- подтверждённые выборы, с источником (тред комментария / чекпоинт), где полезно

**In progress**
- что активно движется и в каком состоянии

**Open questions / waiting on**
- нерешённые комментарии, заблокированные пункты, всё, что требует ввода
  клиента — сформулировано как чёткий ask

**Next up** *(только если очевидно из файла — никогда не изобретать план)*
```

**Report-фрейм на канвасе (предложить, затем создать при согласии)** —
после чатовой сводки предложить: "Хотите оформить это как report-фрейм на
холсте, которым можно поделиться?" Если да — создать фрейм с именем
`Report — [period] — [date]`: размер 1200×auto, размещён в пустом
пространстве холста вдали от рабочих зон; чистый editorial-лейаут: имя
файла/проекта как заголовок, период как подзаголовок, затем четыре секции
выше; использовать собственные доминирующие текстовые стили файла и один
акцентный цвет, взятый из файла, чтобы отчёт совпадал с видом проекта;
щедрые отступы, никакого декора, конкурирующего с контентом; никогда не
размещать поверх или внутри существующей работы.

### Guardrails

- Read-only с одним исключением: report-фрейм. Никогда не менять,
  перемещать или удалять существующую работу.
- Не приписывать ничего людям, если это явно не сказано в комментариях —
  не угадывать, кто что сделал.
- Держать всю чатовую сводку под ~250 слов для daily, ~400 для
  weekly/monthly. Отчёт, который никто не читает — это работа ради работы.
- Если пользователь просит отправить отчёт по почте — предоставить текст,
  готовый к копированию; composing и отправка вне этого скилла.
