# Connect Screens (соединить экраны коннекторами)

## Scope

- **По умолчанию:** каждая SECTION на текущей странице — отдельный флоу.
  Экраны внутри одной секции соединяются, экраны в разных секциях —
  независимы. Если секций нет — все connectable-узлы страницы
  рассматриваются как один флоу.
- **Scope, заданный пользователем:** можно сузить или расширить —
  конкретная секция(и) ("свяжи экраны в секции 'Onboarding'" → только
  секции с этим именем), вся страница ("свяжи все экраны на странице" →
  все connectable-узлы как один флоу, игнорируя границы секций),
  выделенные узлы (если у пользователя есть выделение — связать только
  их как один флоу).

## Workflow

**Примечание об экономии токенов (действует везде):** предпочитать один
вызов `evaluate_script`, который делает кластеризацию + построение сетки +
создание коннекторов для всего флоу, а не несколько мелких round-trip'ов, и
держать возвращаемые данные компактными (счётчики, id, предупреждения), а
не полными дампами узлов. Полная детализация (текст сетки, per-node логи)
возвращается/логируется только когда что-то требует более пристального
взгляда — см. паттерн "log on anomaly, not on success" ниже.

1. **Получить шаблонный коннектор** через стратегию cached-or-create:

   **a. Проверить кэшированный шаблонный коннектор, сначала session-scoped:**
   Если ID шаблонного коннектора уже был разрешён ранее в этой сессии (этот
   прогон, через секции/флоу одного файла) — переиспользовать этот ID
   напрямую и сразу перейти к получению его через `figma.getNodeByIdAsync`.
   Откатываться к свежему поиску по странице только если этот ID не
   резолвится (например `getNodeByIdAsync` вернул null — узел удалён).
   Иначе — через `evaluate_script` искать по ВСЕМ страницам узел типа
   CONNECTOR с именем `"CONNECT-SCREENS-LINE"`:

   ```js
   const pages = figma.root.children;
   for (const page of pages) {
     const found = page.findOne(n => n.type === "CONNECTOR" && n.name === "CONNECT-SCREENS-LINE");
     if (found) return { connectorId: found.id, cached: true };
   }
   return { cached: false };
   ```

   Если найден — получить его через `figma.getNodeByIdAsync(connectorId)` и
   использовать как шаблон. **Закэшировать этот ID на остаток сессии**, чтобы
   последующие флоу/секции в том же прогоне не повторяли поиск по странице.
   **Перейти к шагу 2.**

   **b. Если кэшированного шаблона нет — создать его через файл FigJam:**
   `figma.createConnector()` доступен только в файлах FigJam (whiteboard),
   не в Design-файлах. Чтобы получить коннектор в Design-файл, создать его в
   FigJam-файле и скопировать. Сначала найти доступный FigJam-файл через
   `search_files`:

   ```js
   search_files({ editorType: "whiteboard", editedByUser: true, maxNumResults: 1 })
   ```

   Затем через `evaluate_script` на этом FigJam-файле создать коннектор:

   ```js
   const connector = figma.createConnector();
   connector.connectorLineType = "ELBOWED";
   connector.connectorStartStrokeCap = "NONE";
   connector.connectorEndStrokeCap = "ARROW_LINES";
   connector.strokes = [{ type: "SOLID", color: { r: 0.161, g: 0.161, b: 0.161 }, opacity: 1 }];
   connector.strokeWeight = 4;
   connector.name = "CONNECT-SCREENS-LINE";
   let page = connector.parent;
   while (page && page.type !== "PAGE") page = page.parent;
   return { connectorId: connector.id, pageId: page?.id };
   ```

   Затем через MCP-инструмент `duplicate_nodes` скопировать этот коннектор
   в рабочий файл:

   ```js
   duplicate_nodes({
     taskLabel: "Copy template connector",
     fileKey: <working file key>,
     sourceFileKey: <FigJam file key>,
     sourcePageId: <pageId from previous step>,
     nodeIds: [<connectorId from previous step>]
   })
   ```

   Возвращённый `createdNodeIds[0]` — ID шаблонного коннектора в рабочем
   файле. Получить его через `figma.getNodeByIdAsync(id)`. Убедиться, что
   имя скопированного коннектора `"CONNECT-SCREENS-LINE"`, а `strokeWeight`
   равен `4` (на случай, если свойства изменились при копировании).
   **Закэшировать этот разрешённый ID на остаток сессии**, так же как в
   ветке "найден в кэше" выше. Если любой шаг падает (файл FigJam не
   найден, ошибка создания, ошибка дублирования) — сказать пользователю и
   остановиться.

2. **Определить scope и найти connectable-узлы:**

   **a. По умолчанию (по секциям, с fallback на страницу):**
   Итерировать `figma.currentPage.children`, собрать узлы типа SECTION. Для
   каждой секции найти прямых детей типа FRAME или INSTANCE. **Исключить
   узлы, чьё имя начинается с "Annotation"** — это лейблы уровня секции, не
   шаги флоу. (Это допущение по конвенции именования — реальный экран,
   названный, например, "Annotations page", будет ошибочно исключён.
   Отметить пользователю, если у секции ноль connectable-узлов после этого
   фильтра, на случай, если фильтр съел настоящий экран.) Каждая секция
   формирует отдельный флоу, обрабатываемый независимо. **Если SECTION-узлов
   на странице нет**, откатиться к поведению "вся страница" (шаг 2c) —
   собрать все узлы FRAME и INSTANCE, являющиеся прямыми детьми страницы, и
   рассматривать их как один флоу.

   **b. Пользователь называет секцию(и) по имени:**
   Отфильтровать `figma.currentPage.children` только по SECTION-узлам, чьё
   имя совпадает с вводом пользователя (регистронезависимо). Обрабатывать
   найденные секции так же, как по умолчанию — каждая отдельный флоу.

   **c. Пользователь указывает "всю страницу":**
   Собрать все узлы FRAME и INSTANCE, являющиеся прямыми детьми страницы
   или прямыми детьми любой SECTION на странице. **Исключить узлы, чьё имя
   начинается с "Annotation".** Рассматривать все собранные узлы как один
   флоу.

   **d. Пользователь указывает фильтр по имени** (например "фреймы,
   начинающиеся с 'step'" или "с 'checkout' в имени"): применить фильтр
   поверх базовых критериев (FRAME или INSTANCE, прямые дети секций).

3. **Для каждого флоу построить сетку из connectable-узлов:**

   Группировка узлов в строки/колонки использует **кластеризацию по
   разрывам (gap-based clustering)**, а не фиксированный пиксельный
   допуск, поэтому она адаптируется к любому масштабу фреймов, реально
   используемому во флоу (мобильные макеты, плотные десктопные фреймы и
   т.д.), вместо предположения об универсальной пиксельной полосе.

   **a. Назначить колонки (gap-based кластеризация по x-позиции):**
   Взять x-позицию (левый край) каждого узла. Отсортировать уникальные
   значения по возрастанию: `sortedX`. Вычислить последовательные разрывы:
   `gaps[i] = sortedX[i+1] - sortedX[i]`. Вычислить `medianGap =
   median(gaps)`. Разрыв считается **границей колонки**, если он больше
   `medianGap * 3`. Пройти `sortedX` слева направо, начиная новую группу
   колонки каждый раз, когда пересекается граничный разрыв. Это даёт
   границы колонок без единой захардкоженной пиксельной константы.
   **Tie-breaker для неоднозначных/равномерных сеток:** если все разрывы в
   пределах ~20% друг от друга (ни один явно не больше — например
   идеально равномерная сетка), gap-based кластеризация не находит
   естественной границы. Откатиться на допуск, выведенный из размера:
   `colTolerance = median(node.width по всем узлам) * 0.15`, группировать
   узлы, чьи x-позиции отличаются меньше, чем на `colTolerance`.
   Отсортировать получившиеся группы слева направо. Назначить индексы
   колонок начиная с 1.

   **b. Назначить строки (gap-based кластеризация по y-позиции):**
   Та же процедура, что и (a), применённая к y-позиции (верхний край),
   формирует группы строк. Использовать тот же tie-breaker для равномерной
   сетки (`rowTolerance = median(node.height) * 0.15`), когда разрывы не
   разделяют чисто.

   **c. Проверка перекрытия (обрабатывает несовпадающие размеры фреймов):**
   Gap-based кластеризация по одному краю (лево/верх) всё ещё может
   ошибочно сгруппировать узлы очень разных размеров — например широкий
   фрейм и узкий фрейм, чьи левые края кластеризуются вместе по логике
   разрывов, но чьи вертикальные протяжённости едва пересекаются. Перед
   финализацией группы строк проверить, что каждая пара узлов в ней
   реально пересекается по вертикали минимум на 30% высоты более короткого
   узла:

   ```js
   overlap = min(a.y + a.height, b.y + b.height) - max(a.y, b.y)
   overlapsEnough = overlap > 0 and (overlap / min(a.height, b.height)) >= 0.3
   ```

   Если узел не проходит эту проверку относительно остальной назначенной
   группы строки — переместить его в отдельную строку (или в ближайшую
   строку, с которой он эту проверку проходит). Применить аналогичную
   горизонтальную проверку перекрытия для групп колонок.

   **d. Разместить каждый узел в сетке** на его позиции `(row, col)`.
   Каждая ячейка либо занята одним узлом, либо пуста. Выполнить
   кластеризацию (3a-3c) и построение сетки в том же вызове
   `evaluate_script`, который продолжит созданием коннекторов (шаг 4) —
   один round-trip на флоу, а не один на под-шаг.

   **Log on anomaly, not on success.** По умолчанию возвращать/логировать
   только однострочную сводку: `"4 rows x 3 cols, 11 nodes"`. Выдавать
   полный текст сетки и параметры кластеризации (границы колонок/строк,
   медианный разрыв, порог разрыва) только когда происходит одно из
   следующего, поскольку именно тогда детализация реально нужна для
   диагностики:
   - tie-breaker для равномерной сетки (допуск, выведенный из размера)
     пришлось использовать вместо gap-based кластеризации;
   - проверка перекрытия (3c) переместила узел из изначально назначенной
     строки или колонки;
   - любой узел остаётся с нулём `attachedConnectors` после того, как весь
     шаг 4 отработал (см. 4c).

   ```
   Column boundaries: [x1, x2, x3, ...]  (median gap: Npx, break threshold: Npx)
   Row boundaries: [y1, y2, y3, ...]  (median gap: Npx, break threshold: Npx)
   Grid:
   r1c1: [nodeId]
   r2c2: [nodeId]  r2c3: [nodeId]  ...
   r3c2: [nodeId]  r3c3: [nodeId]  ...
   ```

4. **Пройти сетку и соединить узлы по трём правилам:**

   **a. Соединить вправо:** для каждой занятой ячейки `(row, col)`, если
   `(row, col+1)` занята — соединить этот узел с тем узлом магнитами
   **RIGHT → LEFT**.

   **b. Соединить вниз (fork) — единый проход сверху вниз:**

   Вместо повторного поиска по сетке назад каждый раз, когда начинается
   новая строка, пройти строки сверху вниз один раз, отслеживая последний
   размещённый узел в каждой колонке по ходу (`lastNodeInCol`). Это
   заменяет старый поиск walk-up/shift-left/walk-up-again единым проходом,
   даёт согласованное поведение независимо от формы сетки и естественно
   поддерживает несколько форков из одного исходного узла.

   ```
   lastNodeInCol = {}   // col -> самый недавно размещённый узел в этой колонке

   for row in sorted(occupiedRows):
       for col in sorted(occupiedColsInRow(row)):
           node = grid[row][col]

           if occupied(row, col - 1):
               # обычное продолжение горизонтального прогона
               connect(grid[row][col - 1] -> node, RIGHT -> LEFT)
           elif row > 1:
               # начало нового прогона: найти источник форка, идя влево
               # через уже пройденные колонки, не пере-поиском по сетке
               searchCol = col - 1
               while searchCol >= 1 and searchCol not in lastNodeInCol:
                   searchCol -= 1
               if searchCol >= 1:
                   connect(lastNodeInCol[searchCol] -> node, BOTTOM -> LEFT)
               # если searchCol < 1, источника форка ещё нет — оставить
               # это isolated-node fallback'у (4c)

           lastNodeInCol[col] = node   # обновить ПОСЛЕ обработки этой ячейки
   ```

   Интуиция не изменилась: источник форка — предшественник узла прямо
   сверху (не сам узел сверху), потому что `lastNodeInCol[col]` хранит тот
   узел, что был размещён в этой колонке последним — который, по
   построению, и есть корректный более ранний шаг флоу, был ли он на одну
   строку выше или на несколько.

   **Известное ограничение — точки слияния не обрабатываются:** этот
   проход, как и оригинальный алгоритм, предполагает, что у каждого начала
   новой строки ровно один источник форка (древовидный флоу). Если две
   строки одновременно питают один более поздний узел (слияние), этот
   паттерн здесь не распознаётся, и целевой узел слияния, скорее всего,
   будет пойман isolated-node fallback'ом (4c) вместо семантически верного
   коннектора слияния. Если флоу со слиянием — обычное дело, для этого
   нужно отдельное правило — отметить пользователю, а не молча соединять
   неверно.

   **c. Isolated node fallback:** если у узла ноль `attachedConnectors`
   после правил (a) и (b) — найти ближайшую занятую ячейку по
   евклидовому расстоянию координат сетки и соединить с ней магнитами
   **RIGHT → LEFT**. **Логировать эти fallback-соединения отдельно** от
   основанных на правилах в финальном отчёте (шаг 6) — fallback-соединение
   это догадка, а не обнаруженная связь, и должно быть легко заметно
   пользователю для проверки.

   **d. Дедупликация:** перед созданием любого коннектора проверить
   `attachedConnectors` на обоих концах, чтобы увидеть, не связывает ли уже
   коннектор эти два узла. Пропустить, если уже соединены.

   **e. Создание коннекторов:**
   - Клонировать шаблон: `templateConnector.clone()`
   - Добавить клон в подходящего родителя (секцию, если работа
     по-секционная, или страницу, если по всей странице):
     `parent.appendChild(newConnector)`
   - Задать концы:

   ```js
   // Горизонтально (RIGHT → LEFT):
   newConnector.connectorStart = { endpointNodeId: sourceNode.id, magnet: "RIGHT" }
   newConnector.connectorEnd   = { endpointNodeId: targetNode.id, magnet: "LEFT"  }

   // Вертикально / Fork (BOTTOM → LEFT):
   newConnector.connectorStart = { endpointNodeId: sourceNode.id, magnet: "BOTTOM" }
   newConnector.connectorEnd   = { endpointNodeId: targetNode.id, magnet: "LEFT"   }
   ```

5. **Сохранить шаблон для переиспользования**: НЕ удалять шаблонный
   коннектор после использования. Он остаётся в файле (с именем
   `"CONNECT-SCREENS-LINE"`), чтобы последующие прогоны могли найти и
   переиспользовать его без файла FigJam.

6. **Отчитаться о результатах.** По умолчанию — одна лаконичная сводная
   строка по всем флоу:

   ```
   3 sections: 14 connectors created, 2 fallback, 1 duplicate skipped
   ```

   Разворачивать до детализации по секциям только когда есть что
   отметить:
   - были созданы любые **fallback**-коннекторы (4c) — поскольку это
     догадки по расстоянию, а не обнаруженные связи флоу, перечислить,
     какие пары узлов они соединяют, чтобы пользователь мог их
     перепроверить;
   - любая секция была полностью пропущена, потому что фильтр по имени
     "Annotation" оставил ноль connectable-узлов (см. примечание к 2a);
   - любой узел всё ещё имеет ноль `attachedConnectors` после того, как
     все правила отработали.

   Если ничего из вышеперечисленного не применимо — однострочной сводки
   достаточно, не печатать разбивку по секциям просто потому, что секции
   существуют.

   Сделать скриншот первой секции для визуального подтверждения.
