# improve-codebase-architecture

Порт `improve-codebase-architecture` из mattpocock/skills (MIT), близко к
тексту. Другой этап, чем `dev-architecture`: тот проектирует границу ДО кода,
этот сканирует уже написанный код на предмет "мелких" (shallow) модулей.

## Словарь

Тот же, что в `dev-architecture` (шаг 4б там уже ссылается на deep/shallow) -
глубина (depth), шов (seam), адаптер (adapter), leverage (что получают
вызывающие), locality (что получают поддерживающие). **Deletion test**:
мысленно удалить модуль - если сложность исчезла, это был проходной слой;
если перетекла к N вызывающим, модуль оправдан.

## Порядок

### 1. Разведка

Сначала решить, куда смотреть, не сканировать всё подряд (YAGNI). Если
направление названо явно - взять его. Иначе - пройтись по `git log --oneline`
в поисках горячих точек, прочитать `CONTEXT.md` и ADR в области, куда идёшь.

Искать трение: где понимание одной концепции требует прыжков между модулями,
где интерфейс почти такой же сложный, как реализация, где чистые функции
выделены только ради тестируемости, но баги живут в месте вызова, где
untested-код прячется за неудобным интерфейсом. К каждому подозрению -
deletion test.

### 2. Отчёт кандидатов

Каждый кандидат - карточка: файлы, проблема, решение простым языком, польза в
терминах leverage/locality, диаграмма до/после, метка силы рекомендации
(Strong / Worth exploring / Speculative). В конце - "Top recommendation" с
обоснованием, что делать первым.

Конфликт с существующим ADR - показывать только если трение реальное
настолько, чтобы стоило пересматривать ADR, не листинг всех теоретических
рефакторингов, которые ADR запрещает.

Не предлагать интерфейсы на этом шаге - спросить у пользователя, какой
кандидат интересен.

### 3. Разбор выбранного кандидата

По выбранному кандидату - разбор ограничений, зависимостей, формы модуля, что
сидит за швом, какие тесты переживут изменение. Новый термин, которого нет в
`CONTEXT.md` - добавить туда. Пользователь отклоняет кандидата с весомой
причиной - предложить зафиксировать её ADR-ом, чтобы будущий проход не
предлагал то же самое снова.

## Соседи

Проектирование НОВОГО модуля до кода - `dev-architecture`, не сюда. Дифф уже
написан, ищем баги/дубли - `/code-review`. Общая раздутость всего проекта -
`/ponytail-audit`. Технический долг вне архитектуры (тесты, доки, зависимости)
- `tech-debt-tracker`.
