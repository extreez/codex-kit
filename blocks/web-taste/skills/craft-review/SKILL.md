# craft-review

Сильный интерфейс не пять независимых аудитов, сшитых степлером — иерархию
несут положение и отступ раньше, чем прочитано слово, слова сами всё
объясняют, типографика делает их читаемыми, а полировка — то, что делает
результат осознанным, а не собранным на скорую руку. Ревью проходит по
всему опыту целиком, затем сводится в один приоритизированный вердикт.

## Роль: оркестратор, не хранилище всех правил

Пять доменов, из которых у этого скилла свой только один. Остальные четыре
зовёт как отдельные блоки, не копирует их правила себе — иначе то же самое
правило придётся чинить в двух местах, и они разъедутся.

| Домен | Кто владеет | Статус блока |
|---|---|---|
| Accessibility | `web-a11y-code` (AccessLint) | собран |
| Layout / Typography | `web-fundamentals` | собран |
| Writing | `ux-writing` | собран |
| Motion | `web-motion` | собран |
| **Surfaces / Icons / hero-решения** | **этот скилл** | здесь |

Все пять доменов собраны — реально звать каждый за своей частью, не
подменять чужой домен самодельным ревью здесь.

## Как проводить ревью

### Сначала scope и режим

Вывести экран/поток/фичу/репозиторий из запроса и текущего состояния
проекта. Явно назвать разрешённый scope в выводе. Режим `full`, если не
указан иной.

| Режим | Охват | Потолок находок |
|---|---|---|
| `quick` | основной пользовательский путь и самые частые состояния; только `HIGH`/`MEDIUM` | 5 |
| `full` | весь запрошенный scope, включая пустые/loading/error/узкие состояния | 15 |

Если запрошенный scope слишком велик для честной проверки — сузить до
самого частого целого потока и назвать границу. Никогда не подразумевать,
что непроверенная поверхность была проверена.

### Разведка перед суждением

Определить фреймворк, систему стилизации, библиотеку компонентов,
design-токены, поддерживаемые viewport'ы, доступные команды
preview/тестов. Совпадать со стилевой системой проекта: Tailwind-утилиты в
Tailwind-проекте, обычные декларации в CSS, CSS Modules, styled-components
или StyleX — никогда не вводить вторую систему стилизации ради одного
фикса.

### Доказательность

Каждая находка цитирует `path/to/file:line` и показывает текущую
реализацию. Нет исходников — цитировать точный экран и компонент. Не
репортить находку уровня кода из одного только визуального впечатления, и
наоборот, когда решает runtime-поведение.

### Ревью без мутации по умолчанию

Запрос на ревью — read-only. Не редактировать исходники, если явно не
попросили ещё и внедрить находки. При внедрении сохранять сведённый отчёт
как scope изменений и заново прогонять релевантную проверку после.

## Surfaces — свой домен

### Concentric Border Radius

При вложенных скруглённых элементах внешний радиус обязан равняться
внутреннему плюс отступ между ними:

```
outerRadius = innerRadius + padding
```

Правило особенно полезно, когда вложенные поверхности расположены близко.
Если отступ больше `24px` — считать слои отдельными поверхностями и
выбирать радиус каждой независимо, не форсируя строгую концентричность.

```css
/* Хорошо: концентричные радиусы */
.card { border-radius: 20px; padding: 8px; }      /* 12 + 8 */
.card-inner { border-radius: 12px; }

/* Плохо: одинаковый радиус на обоих */
.card { border-radius: 12px; padding: 8px; }
.card-inner { border-radius: 12px; }
```

Несовпадающие радиусы на близко вложенных поверхностях — частый источник
визуального напряжения.

### Optical Alignment

Когда геометрическое центрирование выглядит неправильно, выравнивать
оптически.

**Кнопки с текстом + иконкой.** Отправная точка: `icon-side padding =
text-side padding - 2px`.

**Play-иконки.** Треугольные иконки, их геометрический центр не
визуальный. Сдвигать чуть вправо: `transform: translateX(2px)`.

**Асимметричные иконки** (звёзды, стрелки, галочки) — лучший фикс
поправить сам SVG, не добавлять margin в коде компонента.

### Shadows for Elevation, Borders for Structure

Для кнопок, карточек и контейнеров, где граница существует только ради
глубины — предпочесть слоистый прозрачный `box-shadow`. Границы,
сообщающие структуру или состояние (разделители, layout-сепараторы,
selected/focus) — оставлять границами.

Светлый режим — три слоя (кольцо-граница, лёгкий подъём, окружающая
глубина):

```css
--shadow-border:
  0px 0px 0px 1px oklch(0 0 0 / 0.06),
  0px 1px 2px -1px oklch(0 0 0 / 0.06),
  0px 2px 4px 0px oklch(0 0 0 / 0.04);
```

Тёмный режим — упростить до одного белого кольца (слоистая глубина не
видна на тёмном фоне):

```css
--shadow-border: 0 0 0 1px oklch(1 0 0 / 0.08);
```

Не применять к дивайдерам (`border-b`, `border-t`, боковые границы) и
любой границе, чья роль — разделение layout, не глубина элемента.

### Image Outlines

Тонкий `1px` outline низкой непрозрачности на изображениях — согласованная
глубина.

**Правила цвета (не обсуждаются):**
- Светлый режим: чистый чёрный, `oklch(0 0 0 / 0.1)`.
- Тёмный режим: чистый белый, `oklch(1 0 0 / 0.1)`.
- Никогда не near-black/near-white из палитры проекта (slate-900, zinc-900,
  `#0a0a0a`). Тонированный outline подхватывает цвет поверхности под собой
  и читается как грязь на краю картинки.
- Никогда не совпадает с акцентным/чернильным цветом проекта — outline
  нейтральный разделитель, не тематический элемент.

```css
img {
  outline: 1px solid oklch(0 0 0 / 0.1);   /* тёмный режим: oklch(1 0 0 / 0.1) */
  outline-offset: -1px; /* кольцо чуть внутри края картинки */
}
```

Почему `outline`, а не `border`: `outline` никогда не влияет на layout (не
добавляет ширину/высоту ни при каком offset), а `outline-offset: -1px`
рисует кольцо чуть внутри края картинки, повторяя её радиус скругления, а
не сидя снаружи.

## Icons — свой домен

### Match Icon Stroke to Text Weight

Иконка рядом с текстом несёт ту же оптическую тяжесть, что и текст, иначе
пара читается несоразмерно.

| Соседний текст | Толщина обводки иконки (сетка 24px) |
|---|---|
| Regular (400), 14-16px | `1.5px` |
| Medium/Semibold (500-600) | `2px` |
| Bold (700), выделенная отдельно | `2.5px` |

Два связанных правила согласованности: одна оптическая стратегия на
поверхность (не мешать библиотеки иконок с разными конвенциями обводки в
одном тулбаре), размер иконки относительно cap-height текста — обычно
`1em`-`1.25em` при инлайне с текстом.

### One SVG, Recolored per State

Никогда не поставлять отдельные ассеты иконки на default/hover/selected/
disabled. Один SVG на `currentColor`, состояние управляется через CSS-цвет
и opacity:

```css
.icon-button { color: oklch(0.552 0.016 285.938); }
.icon-button:hover { color: oklch(0.21 0.006 285.885); }
.icon-button[aria-pressed="true"] { color: oklch(0.623 0.188 259.815); }
.icon-button:disabled { opacity: 0.4; }
```

Захардкоженные заливки внутри самого SVG (`fill="#666"`) ломают это —
зачищать до `currentColor` при импорте иконок.

### Outline Default, Fill Active

Когда набор иконок даёт outline- и filled-варианты, использовать их как
пару состояний, не взаимозаменяемо: outline — дефолт (тулбары, строки
списков, инлайн с текстом), fill — выбранное/активное состояние (активный
таб, включённый bookmark).

### Design at Render Size

Иконка, отлично смотрящаяся на 48px, может превратиться в кашу на 16px.
Тестировать каждую иконку на минимальном размере рендера (часто `16px`) —
должна оставаться узнаваемой. Держать иконки на пиксельной сетке при
размере рендера (`16`, `20`, `24`), не произвольные дробные масштабы.
Всегда SVG, никогда растр.

### Icons in RTL

Под `dir="rtl"` переворачивать иконки, чей смысл завязан на направление
чтения, остальные не трогать.

| Переворачивать | Не переворачивать |
|---|---|
| стрелки назад/вперёд, шевроны в навигации | логотипы и бренд-марки |
| глифы текстового блока (выравнивание, списки, отступ) | галочки |
| волны громкости (излучаются по направлению чтения) | физические объекты (часы, чашки, карандаши) |

Разбирать составные иконки по частям: бейдж или slash-оверлей может
сохранять позицию, даже когда базовый глиф переворачивается.

## Техники: стресс-тест, альтернативы, разбор чужого

Три процессных паттерна из jakubkrehel/skills — не выносят вердикт сами,
ссылаются на доменный скилл-«владельца» находки:

**break** — рендерит компонент во всех сценариях (контент, состояния,
окружение) и репортит только визуально наблюдаемые поломки: «"Text
escapes the field's right edge", never "spacing feels tight"». Предсказанная,
но не отрендеренная поломка не считается находкой — «a run that never
rendered is a code review wearing a costume».

**variant** — генерирует 2-3 альтернативы по одной оси (Structure/Density/
Emphasis/Type/Voice), не по мелочам: «Three variants that differ in accent
color teach nothing». Каждый вариант обязан пройти базовые проверки
(accessible name, keyboard reach, focus visible, 320px, no color-only
meaning) прежде чем считаться кандидатом: «A variant that wins on looks and
fails an escalation trigger is not a candidate. It is a bug with a nice
surface». Варианты рендерятся в реальной странице с реальным контентом, не
в изоляции.

**explain-interface** — разбор чужого UI с обязательной маркировкой
Measured/Derived/Inferred: «Inventing a plausible value and presenting it
as measured is the one failure that makes the whole answer worthless».

Полный текст этих трёх техник — в апстриме (jakubkrehel/skills), здесь
только рабочее резюме, не вендорено дословно.

## Формат вывода

### Scope и охват

Назвать режим, точный scope, стек и конвенции стилизации, границу ревью.
Затем таблица охвата по каждому домену (включая те, что зовутся из других
блоков):

| Домен | Что проверено | Результат |
|---|---|---|
| Surfaces/Icons | ... | находок N или `Clear` |

`Clear` значит проверено, находок нет. `Not reviewed` требует объяснения
почему.

### Находки

Одна таблица, отсортированная по severity, затем по охвату и рычагу:

| # | Severity | Домен | Место | До | После | Почему |
|---|---|---|---|---|---|---|
| 1 | HIGH | Surfaces | `src/Dialog.tsx:42` | `border-radius: 12px` на обоих уровнях | `20px`/`12px` по формуле | несовпадающие радиусы читаются как небрежность |

Severity: `HIGH` блокирует задачу/вводит в заблуждение/скрывает контент;
`MEDIUM` заметно вредит восприятию/эффективности/согласованности; `LOW`
изолированная полировка, только в `full`.

Одна строка на первопричину — перечислить все подтверждённые места в
одной строке, не плодить строку на каждое вхождение.

### Рассмотрено, но отвергнуто

1-3 кандидата в `quick`, 2-5 в `full` — реальные рассмотренные варианты, не
filler.

### Верификация

Прогнать безопасные доступные проверки. Разделить прошедшее и `Not
verified`; никогда не превращать пробел в верификации в находку.

### Вердикт

Ровно один в конце: `Block` (остались HIGH), `Needs changes` (только
MEDIUM/LOW), `Approve` (находок нет, заявленный охват верифицирован).

Конкретная находка на грани HIGH/MEDIUM и решение реально спорно (не
"лень доразобраться", а честно 50/50) — прежде чем зафиксировать
severity, можно вызвать `debate` (Skill tool): одна позиция "это HIGH,
блокирует", другая "это MEDIUM, не блокирует", и решение — по итогу
раундов, не по первому впечатлению. Не для каждой находки — только там,
где сам колеблешься.

## Частые ошибки (свой домен)

| Ошибка | Фикс |
|---|---|
| Одинаковый border-radius на близко вложенных родителе и ребёнке | `outerRadius = innerRadius + padding` |
| Иконки выглядят не по центру | оптическая поправка через padding или правка SVG |
| Граница используется только чтобы имитировать elevation | слоистый `box-shadow` с прозрачностью; структурные/state-границы оставить |
| Тонированный outline на изображении | только чистый чёрный/белый в oklch, никогда near-black палитры |
| Отдельные ассеты иконки на каждое состояние | один `currentColor` SVG, состояния через CSS |
| Filled-иконки везде | outline по умолчанию, fill только для активного |
| Hairline-иконка рядом с bold-текстом | подобрать толщину обводки под вес текста |

## Проверяемый результат (для /loop-build)

Нет команды — craft-review это один целостный вердикт по polish/hero-
решениям, не сумма независимых пунктов. Критерий: verifier-subagent
выносит один PASS/FAIL с конкретной причиной, не голосование нескольких.

## Не параллелить сам вердикт

Целостное суждение специально не дробится — параллельные "мнения" по
кускам одного экрана не складываются в одну оценку целого. Параллелить
можно только между **разными экранами** (subagent на экран), не внутри
одного вердикта.

## Synthesized brand and product rules

Visual character belongs in shape language, type, spacing, color roles,
iconography, imagery, and motion together. Keep the real product visible in
product representations: use truthful labels, numbers, states, and output.
Use hierarchy and contrast to make the primary task obvious, then apply the
brand tone without inventing decorative chrome that the product does not have.
