# Метрики программы

5 инструментов из `Owl-Listener/ux-pgm-skills`, обобщены от UX-
программы до любой программы/проекта. Файлы в `templates/` дословно на
английском, атрибуция в начале каждого.

## Какой инструмент когда

| Запрос пользователя | Файл | Что измеряет |
|---|---|---|
| «измерь эффективность процесса» | `templates/designops-metrics.md` | Cycle time, throughput, blocker age, rework rate, adoption — трение в потоке работы, не производительность людей |
| «сделай дашборд здоровья программы» | `templates/health-dashboard.md` | Один экран: headline-статус, 1-2 outcome-метрики наверху, leading-индикаторы в середине, health-метрики внизу, всегда с целью рядом с фактом |
| «отчитайся об impact программы» | `templates/impact-reporting.md` | Outcome → evidence (baseline + метод) → честная атрибуция → cost → что это значит для будущих инвестиций |
| «определи KPI программы» | `templates/program-kpis.md` | 1-2 lagging (outcome) + leading (ранний сигнал) + health-метрики программы, с источником/формулой/владельцем/кадансом на каждую |
| «наладь операционку исследований» | `templates/research-ops-coordination.md` | Пайплайн участников, согласие/этика, репозиторий инсайтов, каданс исследований, инструменты — нишевое, только если в программе есть своя практика research |

## Как выбирать

**Это не то же самое, что блок `metrics`.** `metrics` (существующий
блок) измеряет продукт/бизнес — North Star, атрибуцию каналов, аналитику.
Этот блок измеряет саму программу/процесс её выполнения — трение,
здоровье, impact работы команды. Одна и та же программа обычно
использует оба: `metrics` для «что происходит с продуктом»,
`program-metrics` для «как работает сама программа, которая этот
продукт делает». Не дубль, разный altitude — как `seo-audit` и
`web-fundamentals` с общими CWV-числами, но разной целью измерения.

`program-kpis` определяет метрики, `health-dashboard` их показывает,
`impact-reporting` рассказывает о них руководству — три стадии одного
пайплайна измерения, не альтернативы.

`research-ops-coordination` — нишевый, применим только если у команды
есть собственная практика пользовательских исследований с
регулярным потоком студий. Не предлагать его программе без research-
практики.
