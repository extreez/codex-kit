# Дизайн A/B-теста

Цель — спроектировать тест, дающий статистически валидный и применимый
результат, а не просто «посмотреть, что получится».

## Перед дизайном

Уточнить:

1. **Контекст теста** — что улучшаем, какое изменение рассматриваем.
2. **Текущее состояние** — базовый conversion rate, объём трафика.
3. **Ограничения** — техническая сложность, сроки, доступные инструменты.

---

## Базовые принципы

1. **Начинать с гипотезы.** Не «посмотрим, что будет» — конкретное
   предсказание результата, основанное на данных или рассуждении.
2. **Тестировать одну переменную.** Иначе непонятно, что сработало.
3. **Статистическая строгость.** Размер выборки определён заранее, не
   подглядывать и не останавливать тест раньше срока, следовать методологии.
4. **Мерить то, что важно.** Primary-метрика привязана к бизнес-ценности,
   secondary — для контекста, guardrail — чтобы не навредить.

---

## Фреймворк гипотезы

### Структура

```
Потому что [наблюдение/данные],
мы считаем, что [изменение]
приведёт к [ожидаемому результату]
для [аудитории].
Поймём, что это так, когда [метрики].
```

### Пример

**Слабая**: «Изменение цвета кнопки может увеличить клики».

**Сильная**: «Потому что пользователи жалуются, что не находят CTA (по
хитмапам и фидбеку), мы считаем, что увеличение кнопки и контрастный цвет
поднимут клики по CTA на 15%+ у новых посетителей. Измеряем click-through
rate от просмотра страницы до старта регистрации».

---

## Типы теста

| Тип | Описание | Нужный трафик |
|---|---|---|
| A/B | Две версии, одно изменение | Умеренный |
| A/B/n | Несколько вариантов | Выше |
| MVT | Комбинации нескольких изменений | Очень высокий |
| Split URL | Разные URL под варианты | Умеренный |

## Sample size

### Быстрая справка

| Baseline | Lift 10% | Lift 20% | Lift 50% |
|---|---|---|---|
| 1% | 150k/вариант | 39k/вариант | 6k/вариант |
| 3% | 47k/вариант | 12k/вариант | 2k/вариант |
| 5% | 27k/вариант | 7k/вариант | 1.2k/вариант |
| 10% | 12k/вариант | 3k/вариант | 550/вариант |

## Выбор метрик

**Primary** — одна метрика, которая решает исход теста, напрямую привязана
к гипотезе.

**Secondary** — поддерживают интерпретацию primary, объясняют, почему/как
изменение сработало.

**Guardrail** — то, что не должно ухудшиться; тест останавливается при
значимом ухудшении.

Пример (тест страницы pricing): primary — plan selection rate, secondary —
время на странице, распределение по планам, guardrail — тикеты в
поддержку, refund rate.

---

## Дизайн вариантов

| Категория | Что варьировать |
|---|---|
| Заголовки/копирайт | Угол сообщения, value prop, конкретность, тон |
| Визуал | Layout, цвет, изображения, иерархия |
| CTA | Текст кнопки, размер, размещение, количество |
| Контент | Состав информации, порядок, объём, social proof |

Изменение должно быть одно, значимое, достаточно смелое, чтобы дать
разницу, и верное гипотезе.

---

## Traffic allocation

| Подход | Сплит | Когда использовать |
|---|---|---|
| Стандартный | 50/50 | По умолчанию для A/B |
| Консервативный | 90/10, 80/20 | Ограничить риск плохого варианта |
| Постепенный | Старт с малого, наращивание | Смягчить технический риск |

Учитывать: пользователь должен видеть один и тот же вариант при повторных
визитах, экспозиция сбалансирована по времени суток/дням недели.

---

## Реализация

**Client-side** — JavaScript меняет страницу после загрузки, быстро
внедрить, возможен flicker. Инструменты: PostHog, Optimizely, VWO.

**Server-side** — вариант определяется до рендера, без flicker, нужна
разработка. Инструменты: PostHog, LaunchDarkly, Split.

## Запуск теста

### Чек-лист перед запуском

- [ ] Гипотеза задокументирована
- [ ] Primary-метрика определена
- [ ] Sample size рассчитан
- [ ] Варианты реализованы корректно
- [ ] Трекинг проверен
- [ ] QA пройден на всех вариантах

### Во время теста

Делать: следить за техническими проблемами, проверять качество сегментов,
фиксировать внешние факторы.

Не делать: подглядывать в результаты и останавливать тест раньше срока,
менять варианты на ходу, добавлять трафик из новых источников.

### Проблема подглядывания (peeking problem)

Смотреть на результаты до достижения нужного sample size и останавливать
тест раньше срока — прямой путь к ложноположительным результатам и
неверным решениям. Размер выборки фиксируется заранее, и от методологии
не отступают.

## Анализ результатов

**Статистическая значимость**: 95% confidence = p-value < 0.05, значит
меньше 5% шанс, что результат случаен. Это порог, не гарантия.

### Чек-лист анализа

1. Достигнут ли sample size? Если нет — результат предварительный.
2. Статистически значим? Проверить доверительные интервалы.
3. Эффект значим практически? Сравнить с MDE, спроецировать влияние.
4. Secondary-метрики согласуются с primary?
5. Есть проблемы с guardrail-метриками?
6. Есть различия по сегментам (mobile/desktop, новые/вернувшиеся)?

| Результат | Вывод |
|---|---|
| Значимый победитель | Внедрить вариант |
| Значимый проигравший | Оставить контроль, разобрать причину |
| Нет значимой разницы | Нужно больше трафика или более смелый тест |
| Смешанные сигналы | Копать глубже, возможно по сегментам |

## Программа непрерывной экспериментации

Отдельный тест ценен сам по себе. Непрерывная программа экспериментов —
актив, который накапливается со временем.

### Цикл эксперимента

```
1. Генерация гипотез (данные, исследования, конкуренты, фидбек клиентов)
2. Приоритизация по ICE
3. Дизайн и запуск теста
4. Анализ результатов со статистической строгостью
5. Победители — в плейбук
6. Новые гипотезы из выводов
→ Повтор
```

### Источники гипотез

| Источник | На что смотреть |
|---|---|
| Аналитика | Точки отвала, слабо конвертящие страницы, недоперформящие сегменты |
| Исследования пользователей | Боли, замешательство, неоправданные ожидания |
| Конкуренты | Фичи, посылы, UX-паттерны, которых нет у вас |
| Тикеты поддержки | Повторяющиеся вопросы или жалобы про конверсионные флоу |
| Хитмапы/записи сессий | Где пользователи медлят, rage-click или уходят |
| Прошлые эксперименты | «Значимый проигравший» часто подсказывает новый угол |

### Приоритизация по ICE

Каждую гипотезу оценивают от 1 до 10 по трём осям:

| Ось | Вопрос |
|---|---|
| **Impact** | Если сработает, насколько сильно сдвинет primary-метрику? |
| **Confidence** | Насколько уверены, что сработает (на основе данных, не интуиции)? |
| **Ease** | Насколько быстро и дёшево запустить и измерить? |

**ICE Score** = (Impact + Confidence + Ease) / 3

Первыми запускают эксперименты с высшим счётом. Переоценка — ежемесячно,
контекст меняется.

### Темп экспериментов

| Метрика | Ориентир |
|---|---|
| Запущено экспериментов в месяц | 4-8 для большинства команд |
| Win rate | 20-30% типично для зрелых программ (устойчиво более высокий rate может значить, что гипотезы слишком осторожные) |
| Средняя длительность теста | 2-4 недели |
| Глубина бэклога | 20+ гипотез в очереди |
| Накопленный lift | Совокупный выигрыш от всех победителей |

### Плейбук эксперимента

Когда тест выигрывает, недостаточно просто внедрить его — нужно
задокументировать паттерн:

```
## [Название эксперимента]
**Дата**: [дата]
**Гипотеза**: [гипотеза]
**Sample size**: [n на вариант]
**Результат**: [победитель/проигравший/неопределённо] — [primary-метрика]
изменилась на [X%] (95% CI: [диапазон], p=[значение])
**Guardrails**: [метрики и их результат]
**Различия по сегментам**: [заметные отличия по устройству, сегменту, когорте]
**Почему сработало/не сработало**: [анализ]
**Паттерн**: [переиспользуемый вывод — например, «social proof рядом с
CTA увеличивает выбор плана»]
**Применить к**: [другие страницы/флоу, где паттерн может сработать]
**Статус**: [внедрено / отложено / нужен follow-up тест]
```

Со временем плейбук становится библиотекой проверенных паттернов роста,
специфичных для конкретного продукта и аудитории.

### Ритм экспериментов

- **Еженедельно (30 мин)**: проверить запущенные эксперименты на
  технические проблемы и guardrail-метрики. Не объявлять победителя
  раньше срока — но останавливать тест, если guardrail значимо ухудшился.
- **Раз в две недели**: завершить готовые эксперименты, проанализировать
  результаты, обновить плейбук, запустить следующий из бэклога.
- **Ежемесячно (1 час)**: пересмотреть темп экспериментов, win rate,
  накопленный lift. Пополнить бэклог гипотез. Переприоритизировать по ICE.
- **Ежеквартально**: аудит плейбука — какие паттерны применены широко,
  какие выигрышные паттерны ещё не масштабированы, какие участки воронки
  недотестированы.

## Частые ошибки

**Дизайн теста**: слишком маленькое изменение (неразличимо), слишком
много изменений сразу (не изолировать эффект), нет чёткой гипотезы.

**Выполнение**: остановка раньше срока, правки по ходу теста, не
проверена корректность реализации.

**Анализ**: игнорирование доверительных интервалов, выборочное
рассмотрение сегментов (cherry-picking), переинтерпретация неопределённого
результата.

## Вопросы для уточнения задачи

1. Какой текущий conversion rate?
2. Сколько трафика получает эта страница?
3. Какое изменение рассматриваете и почему?
4. Какое минимальное улучшение стоит детектировать?
5. Какие инструменты доступны для теста?
6. Тестировали ли этот участок раньше?
