# Визуальные подтипы (куратор-список)

> Таксономия организована по cathrynlavery/diagram-design (39 типов, MIT),
> формулировки ниже собственные, не дословный перевод их type-*.md файлов.
> Полный список из 39 типов: `github.com/cathrynlavery/diagram-design`,
> `skills/diagram-design/references/type-*.md`.

Типы, которые здесь не перечислены (bar, line, scatter, radar, polar,
treemap, quadrant, venn) относятся к данным с числами, не к структуре -
искать их в `chart-selection`, не здесь.

## Architecture (из чего состоит система)

**high-level.** Меньше 7 боксов, для читателя, которому не важна
инфраструктура, важна общая форма продукта. Антипаттерн: пытаться впихнуть
детали деплоя туда, где нужен только общий контур.

**architecture (детальная).** Компоненты + границы + протоколы связи. До 12
узлов по правилу шага 3 SKILL.md. Антипаттерн: рисовать все известные
сервисы вместо тех, что отвечают на заданный вопрос.

**deployment.** Инфраструктурный слой: где что физически/облачно запущено.
Не смешивать с логической архитектурой в одном рисунке - разные вопросы,
разные диаграммы.

**layers (layer stack).** Слоистая система (сеть, governance, кэш) сверху
вниз или снизу вверх с подписанной ролью каждого слоя. Антипаттерн: слои
одинаковой визуальной тяжести, когда по смыслу они не равнозначны.

**nested (containment).** Границы вложенности важнее порядка компенсации,
подходит для "что внутри чего" (VPC внутри региона, модуль внутри пакета).

**dependency.** Направленный граф "что от чего зависит", не архитектура
компонентов, а граф связей одного типа отношений.

**db-schema / er.** Таблицы + ключи + кардинальность связей. Кардинальность
подписывать явно (1:N, N:M), не полагаться на форму стрелки без подписи.

**uml-class.** Классы + методы + отношения наследования/композиции, для
кода, а не для инфраструктуры.

## Workflow (в каком порядке идёт процесс)

**flowchart.** Решения и ветвления с явными условиями на рёбрах ("да"/"нет"
подписаны, не подразумеваются формой стрелки).

**process.** Линейная или почти линейная последовательность шагов без
сложного ветвления - когда сложность в порядке, а не в развилках.

**swimlane.** Строки это владельцы/роли/системы, не семантические слоты
(для семантических слотов см. паттерн 2 в `semantic-patterns.md`).

**kanban.** Статусные колонки с карточками, для рабочего процесса, где важно
текущее распределение работы по стадиям, не единичный прогон.

**fishbone (ishikawa).** Причины, ведущие к одному следствию, сгруппированные
по категориям. Не подходит для процесса во времени, только для анализа
причин.

**loop.** Циклический процесс без явного конца (retry, polling,
continuous-improvement цикл). Антипаттерн: рисовать линейной стрелкой то, что
на самом деле возвращается к началу.

## Sequence (кто кого вызывает по времени)

**sequence.** Участники + сообщения по вертикальной оси времени. Лимит 5
lifelines на одной диаграмме, больше - разбить на несколько сцен.

**dp-integration.** Интеграция между системами данных с явными
точками синхронизации/асинхронности, разновидность sequence под
дата-пайплайны.

## Dataflow (откуда данные приходят, что их трансформирует)

**data-flow.** Источники → трансформации → приёмники, с подписанным
направлением на каждой стрелке.

**sankey.** Пропорциональные потоки между стадиями, толщина линии кодирует
объём. Не путать с bar chart: здесь важна структура перетока, а не сравнение
отдельных величин.

**medallion (bronze/silver/gold).** Специфичный паттерн дата-инженерии:
слои очистки данных от сырых до готовых к использованию, каждый слой
подписан своим уровнем готовности.

## Lifecycle (в каких состояниях бывает объект)

**state.** Состояния + переходы + условия перехода, подписанные на рёбрах,
не подразумеваемые.

**it-state.** Специализация state под IT-инциденты/тикеты (open → in
progress → resolved → closed, с возможными возвратами).

**journey (customer/user journey).** Состояния читаются как этапы опыта
пользователя, а не системы; на каждом этапе - точка соприкосновения и
эмоция/проблема, не только статус.

**timeline.** Хронология событий без ветвления состояний, для истории того,
что уже произошло, не того, что может произойти.

**gantt.** Временные интервалы задач с зависимостями между ними, для
планирования, не для истории. Не путать с timeline: gantt показывает
длительность и параллельность, timeline - точечные события.

## Организационные и стратегические (вне пяти категорий archify)

**org-chart.** Иерархия людей/ролей. Простейший тип с готовой семантикой,
не требует отдельного паттерна.

**wardley.** Карта стратегической ценности vs зрелости компонента. Нишевый
тип, применять только если пользователь явно просит стратегическую карту, не
как замену architecture.

**tree / pyramid.** Чистая иерархия без дополнительной семантики связей,
для классификаций и приоритетов сверху вниз.

**story-map.** Пользовательские активности в строке + релизные срезы в
столбцах, специфично для планирования продукта.
