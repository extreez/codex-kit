# academic-research

Конвейер `question -> evidence -> experiment -> analysis -> claim -> writing`
из `claude-scholar` (MIT), упрощённый до формата codex-kit: без Zotero/
Obsidian-интеграции по умолчанию, без собственной базы знаний - обычные файлы
в `docs/`. Архитектура генерации в 4 фазы (Research -> Structure -> Integration
-> Rendering) из `claude-scientific-writer` (MIT) определяет, что происходит
внутри шага "черновик".

Не переизобретает то, что уже есть в codex-kit: литобзор делает `research-deep`,
проверку фактов и цитат - `fact-check`, стилевую правку текста - `de-ai-text`.
Этот блок добавляет то, чего в них нет: постановку научного вопроса,
венюспецифичные шаблоны, черновик статьи, anti-leakage protocol, claim-drift
guard, style calibration, disclosure-таблицу, опциональный рендер в PDF/DOCX.

## Порядок

### Шаг 0. Модель и эффорт под каждую роль (спросить всегда)

Перед запуском субагентов спроси у пользователя модель и эффорт под каждую
роль отдельно - роли разные по стоимости и по риску отсебятины. Предложи
разумное, дай поправить:

- `paper-drafter`: пишет много текста подряд - opus или effort high, ошибка
  здесь (отсебятина, слишком уверенный тон) дороже чинить постфактум, чем
  переплатить на генерации.
- Anti-leakage и claim-drift проверки (шаги 5-6, прямые шаги скилла, не
  отдельный агент - объём работы не оправдывает субагента): sonnet, effort
  medium, механическая сверка черновика с заметками.
- `research-deep`, `fact-check`, `de-ai-text` спросят про свои роли сами при
  вызове - не задавай за них.

### Шаг 1. Ideation - прояснить вопрос

Расплывчатая тема ("напиши что-нибудь про X") - не начинай литобзор, сначала
задай уточняющие вопросы: какой конкретно пробел в знании закрывает статья,
для какой аудитории/издания, какой ответ пользователь уже подозревает
(гипотеза) и что будет считать статью законченной. Запиши в `docs/question.md`
(тот же формат, что использует `research-deep`) - поля "Что выясняем", "Зачем,
какое решение принимаем", "Что будет считаться достаточным ответом".

Конкретный вопрос с ясным пробелом - можно пропустить уточнения и сразу
заполнить `docs/question.md` по словам пользователя.

### Шаг 2. Литобзор - вызвать research-deep, не собирать с нуля

Передай скиллу `research-deep` вопрос из `docs/question.md` с пометкой, что
это академический контекст: источники предпочтительно T1 (шкала T1-T5 уже
есть в `fact-check`/`research-deep`, не изобретай новую) - научные статьи,
не отозванные, официальная документация методологии. Тир глубины (light/full/
dissertation) выбирай по объёму работы: тезисы конференции - light, полная
статья с несколькими claim - full, systematic review - dissertation.

Semantic Scholar / OpenAlex / Crossref / arXiv verification API - опциональное
усиление для тех, у кого есть доступ, упомяни пользователю как возможность,
не как обязательную зависимость (по аналогии с тем, как в стеке SEO платные
API вынесены в отдельную опцию, не встроены по умолчанию). Без доступа -
`research-deep` работает через обычный WebSearch/WebFetch, этого достаточно.

Ещё один опциональный усилитель — **Parallel Search API** (`claude-scientific-writer`
ходит в него за живым поиском по PubMed/arXiv/CrossRef во время генерации):
`parallel-cli login` или переменная `PARALLEL_API_KEY`. Не встраивай как
зависимость — упомяни, если пользователь спросит про более точный/быстрый
поиск литературы, чем даёт обычный WebSearch. Общий выбор между всеми
поисковыми/парсинг-усилителями (Firecrawl/Exa/Tavily/Apify, не только
Parallel Search) — `library/research-search-mcp`, сверься с ним, если нужен
не конкретно академический, а любой более сильный источник данных.

Результат - `docs/research/notes/*.md` с заметками и `docs/research/report-*.md`
с отчётом. Это единственный источник фактов для черновика статьи, дальше
черновик пишется только из них (см. anti-leakage, шаг 5).

### Шаг 3. Структура по венюспецифичному шаблону

Спроси пользователя, под какой формат готовится текст, если не сказано прямо
- шаблон определяет структуру черновика:

| Формат | Структура |
|---|---|
| IMRaD (журнальная статья) | Introduction, Methods, Results, and Discussion |
| Тематический обзор / литобзор | по тематическим разделам, не по хронологии источников |
| Case study | Background, Case Description, Discussion, Conclusion |
| NSF/NIH/DOE/DARPA грант | Specific Aims, Significance, Approach, Budget Justification - формат бюджета под конкретное агентство, не универсальный |
| Тезисы/постер конференции | сжатая версия IMRaD под лимит символов/слайдов конкретной конференции; сама вёрстка постера - LaTeX-класс `beamerposter`, `tikzposter` или `baposter` (три конкурирующих класса, не выбор блока - спросить у пользователя, требует ли конференция конкретный, иначе предложить `tikzposter` как самый простой в разметке) |
| Nature-семейство | структура конкретного журнала (Nature/Nature Communications и т.д. расходятся в требованиях к абстракту и лимиту слов) - уточни у пользователя журнал, не угадывай общий "Nature-стиль" |

Не угадывай формат по умолчанию - каждый венюспецифичный шаблон меняет, что
считается обязательной секцией, а что лишней. Нет ответа от пользователя -
предложи IMRaD как самый общий дефолт и явно скажи, что это предположение.

**Стиль цитирования** - выбирается вместе с форматом, не отдельно: APA 7.0
(Nature-семейство, большинство социальных/поведенческих наук), IEEE (ML/CS-
конференции, ICLR/NeurIPS), Vancouver (медицинские журналы, ICMJE-стандарт),
Chicago (гуманитарные науки), MLA (реже, часть гуманитарных журналов). Спроси
явно, если пользователь не назвал журнал/конференцию напрямую - у каждого
издания обычно свой обязательный стиль, не общий выбор блока. `fact-check`
и `research-deep` собирают `source_url`/тир, финальное форматирование под
конкретный стиль - здесь, на этом шаге, не раньше.

### Шаг 4. Черновик - agents/paper-drafter.md

Запусти `paper-drafter` с: вопросом (`docs/question.md`), заметками литобзора
(`docs/research/notes/`), отчётом (`docs/research/report-*.md`), выбранным
шаблоном (шаг 3), примерами голоса пользователя, если дал (шаг 5.5).

Integration Phase (из архитектуры `claude-scientific-writer`): если пользователь
дал собственные данные - CSV с результатами эксперимента, изображения фигур,
XLSX с таблицами - агент встраивает их в соответствующие разделы (Results/
Data), не выдумывает данные взамен. Нет данных - раздел Results/Findings
строится только из заметок литобзора, с explicit пометкой, что это
литературный обзор, а не оригинальный эксперимент, если пользователь не
подтвердил обратное.

Диаграммы и схемы, если формат их требует: **CONSORT** (флоу-диаграмма отбора
участников - обязательна для клинических испытаний по требованиям большинства
медицинских журналов из таблицы disclosure, шаг 10), схемы пайплайна/архитектуры
для ML/CS-статей. Рисуй в LaTeX (TikZ) или markdown-совместимом виде (Mermaid),
не растровым изображением, если формат вывода - markdown/LaTeX: текстовое
описание схемы правится точечно, картинка - нет.

### Шаг 5. Anti-Leakage Protocol (пересказано своими словами из academic-research-skills)

Отдельная проверка, строже обычного fact-check: fact-check проверяет, подтверждён
ли факт источником; anti-leakage проверяет, есть ли у черновика вообще
основание писать утверждение - собирался ли под него материал в шаге 2, до
того как fact-check его тронет.

Пройди черновик абзац за абзацем. По каждому фактическому утверждению
(не мнению, не связке) - есть ли в `docs/research/notes/` заметка, из которой
оно следует? Нет - утверждение взято из общих знаний модели, а не из
собранного материала. Пометь прямо в тексте: `[ПРОБЕЛ МАТЕРИАЛА: <что нужно
проверить>]`. Не переписывай под уверенный тон, не убирай пометку молча -
решение, добить ли материал новым раундом `research-deep` или оставить как
признанное ограничение, за пользователем.

### Шаг 6. Claim-Drift Guard (пересказано своими словами из academic-research-skills)

Отдельная, специфичная для научного письма проверка - не путать с общим
`de-ai-text` (тот правит стиль, не причинную строгость) и не с `fact-check`
(тот сверяет факт с источником, не силу формулировки вывода).

Шкала строгости причинности, по возрастанию: **ассоциация** ("X связано с Y",
"наблюдается корреляция") **< предсказание** ("X предсказывает Y", "модель
на основе X предсказывает Y с точностью N") **< причинность** ("X вызывает
Y", "X приводит к Y").

Пройди каждый вывод черновика: формулировка в тексте не должна быть сильнее
по этой шкале, чем то, что показывают данные из заметок литобзора (шаг 2).
Заметка описывает корреляционное исследование - вывод в черновике не должен
молча звучать как "X вызывает Y" только потому, что так увереннее читается.
Расхождение - откати формулировку до уровня, который подтверждают данные, и
зафиксируй это в списке правок (шаг 9 отчёта агенту-драфтеру или прямо
Edit'ом, если правка точечная).

### Шаг 5.5 (до или во время шага 4). Style Calibration (пересказано своими словами из academic-research-skills)

Пользователь дал примеры своих прошлых текстов - передай их `paper-drafter`
как образец голоса, мягко подстроиться под интонацию и синтаксис автора, не
переписывать под нейтральный шаблон по инерции. Примеров нет - использовать
разумный дефолт по дисциплине (нейтральный академический тон), не выдумывать
голос, которого никто не просил.

### Шаг 7. Верификация цитат и утверждений - вызвать fact-check

Отдай черновик (после anti-leakage и claim-drift правок) скиллу `fact-check`.
Не изобретай отдельный claim-hunter/claim-skeptic внутри этого блока -
`fact-check` уже делает эту работу: извлечение утверждений, тиры T1-T5,
retraction sweep, вердикт CONFIRMED/REFUTED/UNVERIFIED, `claim_ledger.json`.

REFUTED и отозванные источники - обязательная правка перед сдачей. UNVERIFIED
с высокой значимостью для аргумента статьи - решение за пользователем, оставить
с пометкой пробела или убрать тезис.

### Шаг 8. Стилевая правка текста - вызвать de-ai-text

Финальный проход перед сдачей - скилл `de-ai-text` на готовый текст статьи.
Не копируй список клише и шаблонных слов заново, это уже сделано там. Единственная
поправка для академического контекста: черновик может законно содержать
формальные academic hedges ("results suggest", "these findings indicate") -
это не то же самое, что немотивированное хеджирование из чеклиста `de-ai-text`
("возможно, стоит"), не путать научную осторожность с пустым смягчением при
правке.

### Шаг 9. Форматы вывода

Markdown - всегда, финальный текст живёт в `docs/paper.md` (или где укажет
пользователь) вне зависимости от остального.

LaTeX/PDF - опционально, два варианта движка, проверь оба перед тем как
сказать пользователю, что PDF не соберётся:

- **tectonic** (`tectonic --version`) - самодостаточный статический бинарник,
  сам качает нужные пакеты TeXLive по требованию, ставится одной командой
  (`cargo install tectonic` / `brew install tectonic` / `scoop install tectonic`
  на Windows) без полной установки TeXLive - предпочтительный вариант, если
  доступен, именно его использует `claude-scientific-writer`.
- **pdflatex/latexmk** (`pdflatex --version`) - fallback, если tectonic не
  ставился, а полный TeXLive уже есть в системе.

Ни того ни другого нет - явно скажи пользователю, что деградировали до
markdown, PDF не собран, не притворяйся, что сборка прошла. Постеры
(`beamerposter`/`tikzposter`/`baposter`, шаг 3) собираются тем же движком.

DOCX/PPTX/XLSX - опционально через LibreOffice (`soffice --headless --convert-to`),
та же логика: есть инструмент - конвертируй, нет - скажи прямо и оставь
markdown.

BibTeX - собери из `source_url`/тиров заметок `docs/research/notes/`,
форматируй записи под стиль, выбранный на шаге 3 (APA/IEEE/Vancouver/Chicago/
MLA) - не отдавай сырой BibTeX без учёта того, какой стиль требует издание.

### Шаг 10. Disclosure Statement

Спроси пользователя, под какое издание/конференцию готовится текст - не
угадывай, разные издания требуют разного раскрытия:

| Издание/тип | Что раскрывать |
|---|---|
| ICLR, NeurIPS | Reproducibility statement, заявление об использовании LLM в подготовке текста (обязательно с 2023+ у большинства ML-конференций) |
| Nature, Science | Conflict of interest, funding statement, data/code availability, вклад каждого автора (CRediT) |
| ACL, EMNLP | Limitations section (обязательный отдельный раздел, не сноска), ethics statement при работе с данными о людях |
| Медицинские (ICMJE-стандарт: NEJM, Lancet, JAMA, BMJ, PLOS, Frontiers) | Conflict of interest по форме ICMJE, funding, IRB/этическое одобрение при работе с пациентами, отдельная политика по использованию ИИ у каждого журнала - уточнить конкретный журнал, не считать медицинские издания одинаковыми |
| NSF/NIH/DOE/DARPA грант | Biosketch, Current and Pending Support, Facilities statement - формат конкретного агентства, не общий |

Не собранная информация об издании - оставь секцию disclosure как явный
плейсхолдер с пометкой, какое именно издание нужно уточнить, не выбирай
формат наугад.

## Anti-Leakage vs fact-check - в чём разница (не спутать на практике)

`fact-check` спрашивает: "этот факт подтверждён источником?" Anti-leakage
спрашивает: "у автора вообще было основание это написать - собирал ли он
материал под этот тезис?" Утверждение может быть технически верным (даже
случайно совпасть с источником, которого драфтер не видел) и всё равно быть
utверждением без основания в собранном материале - это и есть находка
anti-leakage, не fact-check.

## Границы

- Не пишет литобзор с нуля - вызывает `research-deep`.
- Не проверяет цитаты и факты сам - вызывает `fact-check`.
- Не делает стилевую правку текста сам - вызывает `de-ai-text`.
- Не собирает LaTeX/PDF/DOCX без реального инструмента в системе - явно
  сообщает о деградации до markdown, не выдаёт желаемое за сделанное.
- Не выбирает издание и его disclosure-требования за пользователя.
- Не заменяет решения человека: выбор проблемы, значимых источников,
  гипотезы, финальное решение о публикации - это позиционирование
  "semi-automated research assistant" из `claude-scholar`, не полностью
  автономная система.
