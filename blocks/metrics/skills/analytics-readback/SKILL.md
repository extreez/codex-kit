# Analytics readback

## Принцип

Любое маркетинговое действие (новый заголовок, изменение цены,
рекламный креатив, SMM-формат) — гипотеза, не факт, пока не измерен
результат после публикации. Читать интуицию/мнение как сигнал для
приоритизации, не как доказательство эффекта — доказательство даёт
только readback.

## Формат readback

```markdown
## Readback: [название изменения]

**Baseline window**: [период до изменения, с датами]
**Candidate window**: [период после изменения, с датами — сопоставимой
длины и сезонности с baseline]
**Метрика-победитель**: [одна главная метрика решения, не список из
десяти]
**Результат**: [цифра/направление, доверительный интервал если
применимо]
**Ограничения**: [что могло исказить сравнение — сезонность, другое
одновременное изменение, малая выборка]
**Решение**: [promote / rollback / нужно больше данных]
```

## Правила продвижения (promote)

- Baseline и candidate window сопоставимы по длине и сезонности —
  сравнивать понедельник с воскресеньем или высокий сезон с низким
  без поправки не годится.
- Изменение метрики отличимо от шума — для достаточного трафика
  использовать статистическую значимость (см. `ab-testing`), для
  малого трафика — явно пометить результат как предварительный, не
  выдавать за подтверждённый.
- Нет другого одновременного изменения, которое могло дать тот же
  эффект (совпавшая по времени PR-публикация, сезонный пик спроса).

Если хотя бы одно правило нарушено — решение «нужно больше данных»,
не promote и не rollback.

## Границы безопасности

| Действие | Уровень |
|---|---|
| Чтение аналитики, сравнение периодов | Read-only, без ограничений |
| Изменение живой кампании/страницы на основе readback | Требует approval человека перед применением |
| Откат (rollback) при явно отрицательном результате | Может быть автоматическим правилом, если порог заранее согласован с человеком |

## Куда встраивается

Скилл вызывается как финальный шаг из: `seo-loop`/`geo-loop` (уже
использовали этот принцип для SEO/GEO — здесь общий формат для
переиспользования), `paid-ads` (после теста креатива/аудитории),
`social-media` (после смены формата/платформы), `content-strategy`
(READBACK-стадия в `content-governance`), `email-outbound` (после
A/B правки цепочки).

## Частые ошибки

- Promote по результату за слишком короткий candidate window (1-2 дня)
  — недостаточно данных, особенно при выраженной внутринедельной
  сезонности.
- Игнорирование одновременных изменений — приписывание всего эффекта
  одной гипотезе, когда сработало что-то ещё, случившееся в то же
  окно.
- Readback выполняется нерегулярно/только для успешных инициатив —
  систематическая ошибка выжившего: неудачные изменения не проверяются
  и не документируются как урок.

## Вопросы для уточнения задачи

1. Какое изменение проверяется и когда оно было применено?
2. Есть ли baseline-период сопоставимой длины/сезонности?
3. Был ли трафик/выборка достаточны для статистической значимости,
   или нужна пометка «предварительно»?
