# sec-audit

Ядро стека `secure`. Находит уязвимости статически: детект стека → поисковики по
зонам → верификация каждой находки другим агентом → отчёт с файлом и строкой.

Правила берёт из `sec-policy` (мастер-чеклист). Своих правил не заводит.

## Свежая сессия

Гоняй аудит сессией, которая код не писала. Кто писал, защищает своё детище и
проскакивает свои же дыры.

## Порядок

### Шаг 0. Модель и эффорт (спросить всегда)

Перед запуском субагентов спроси у пользователя модель и эффорт под роли, количество субагентов (возможно придётся воспользоваться fork или worktree или branch, чтобы оставленные метки другие агенты не видели). Правило
обязательное. Предложи разумное:
- Поисковики (`sec-hunter`): их много, читают код — sonnet, effort medium.
- Верификаторы (`sec-verifier`): решают судьбу находки — opus, effort high, или
  другая модель, чем у поисковика (см. «недоверие»).
- Верификация другой моделью крепче: gemini/gpt через ocx-агентов ловят то, что
  своя модель считает нормой.

Не зашивай модель в агента. Передавай через параметр при запуске.

### Шаг 1. Детект стека

Определи стек по маркерам (`references/zones.md`, таблица детекта). Запиши, что
нашёл: язык, фреймворк, БД, BaaS (Supabase/Firebase), контейнеры. Это фокусирует
поисковиков.

### Шаг 2. Самоадаптация под стек

Стек не в таблице или необычный — предложи создать проектный под-чеклист, сходи в интрнет за свежей документацией и воспользуйся context7:
`.agents/skills/sec-<стек>/SKILL.md` в проекте. Туда — проверки, специфичные для
этого стека, которых нет в язык-агностик чеклисте. Мастер-чеклист не переписывай,
только дополняй проектным. Так набор растёт под реальные проекты пользователя.

### Шаг 3. Поисковики по зонам (параллельно)

Запусти по одному `sec-hunter` на зону Z1..Z11. Каждому дай: id зоны, пункты
чеклиста зоны, корень проекта, детект стека как ГИПОТЕЗУ (не факт — пусть
проверит сам).

Недоверие зашито в агента: он не видит выводов других поисковиков, читает код
сам, возвращает находки с файлом и строкой.

### Шаг 4. Верификация (параллельно, крест-накрест)

Каждую находку отдай `sec-verifier`. Правила:
- Верификатор НЕ тот, кто нашёл (у поисковика нет доступа к своей находке на
  этом шаге).
- По возможности модель верификатора ≠ модель поисковика.
- Верификатор пытается ОПРОВЕРГНУТ находку, перечитывая код с нуля.

Оставляй только `CONFIRMED`. `REFUTED` и `HARDENING` уходят в отчёт отдельными
списками (что проверено и почему не подтвердилось, что осталось пожеланием) — это
тоже результат. Severity ставит верификатор по `sec-policy/references/severity.md`.

### Шаг 5. Отчёт

Два файла рядом: человекочитаемый и машиночитаемый.

**`docs/security/audit-<дата>.md`** (или куда скажет пользователь):
- **Подтверждённые находки**: severity, id, зона, файл:строка, угроза, эксплойт
  (профиль/действие/результат), fix_hint. Сортировка по severity.
- **Хардненинг**: gap при живом соседнем слое — пожелание, не дыра.
- **Опровергнутые**: id, почему сняли (какая проверка закрывает).
- **Не покрыто**: зоны без файлов, что не смог прочитать, лимиты прохода. Молчать
  о пропусках нельзя — иначе отчёт читается как «всё проверено».
- **Чеклист**: таблица пункт → статус (закрыт / дыра / не применимо / не проверено).

**`docs/security/findings.json`** — машиночитаемый, для `sec-loop` и следующего
прохода. Массив находок: `{id, zone, severity, file, line, verdict, exploit,
fix_hint, run}`. Условие остановки цикла читается отсюда, не из глазами.

Не разводи отчётность (правила в `docs/security/AGENTS.md`): всё закрыто — строка
в `LATEST.md`, неактуальные отчёты удаляй.

### Прошлый проход

Есть `findings.json` от прошлого раза — прочитай его перед раздачей зон: пропусти
уже закрытое, целься в непокрытое, разреши конфликтующие вердикты свежей
проверкой. Не начинай с нуля, если проход уже был.

## Независимый второй взгляд

Прогони встроенный `/security-review` по тем же изменениям — это другой
инструмент, не твои субагенты. Расхождение с ним важнее совпадения: где он нашёл,
а ты нет (или наоборот) — разбери. Тот же принцип недоверия, только к самому
аудиту: чужой сканер перепроверяет твой.

## Дальше

- Закрыть находки тестами: блок `sec-tests` (падающий тест на каждый CONFIRMED).
- Проверить атакой: блок `sec-attack` (красная команда по localhost).
- Гонять до нуля: блок `sec-loop`.

## Границы

- Аудит не чинит код. Находит и верифицирует. Фикс — отдельным шагом, после того
  как пользователь посмотрел отчёт.
- Не запускает приложение и не бьёт по сети. Это `sec-attack`.
