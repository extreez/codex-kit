# sec-tests

Превращает находку в проверяемый факт. На каждую подтверждённую уязвимость —
тест, который **падает на текущем коде** и **зеленеет после фикса**. Так находка
доказана, а фикс не откатится молча позже.

Находки берёт из отчёта `sec-audit`. Правила и критерии закрытия — из `sec-policy`.

## Главный принцип: red перед green

Тест сначала должен упасть на непочиненном коде. Не упал — тест ничего не
проверяет (или дыры нет). Это и есть проверка находки тестом:

1. Написал тест под находку.
2. Прогнал на текущем коде — **должен упасть** (red). Не упал — разберись:
   находка ложная или тест мимо. Не двигайся дальше с зелёным тестом.
3. Починил код (или пользователь починил).
4. Прогнал снова — **должен пройти** (green).
5. Тест остаётся в репозитории как регресс.

## Порядок

### Шаг 0. Модель и эффорт (спросить всегда)

Спроси модель и эффорт под написание тестов. Обычно достаточно sonnet
medium; сложные эксплойт-тесты (гонки, вебхуки) — opus high.

### Шаг 1. Детект тест-раннера

Определи, чем проект тестируется, по маркерам:

| Маркер | Раннер | Команда |
|---|---|---|
| `jest` в deps, `*.test.js` | Jest | `npx jest` |
| `vitest` | Vitest | `npx vitest run` |
| `pytest`, `test_*.py` | pytest | `pytest` |
| `go.mod`, `*_test.go` | go test | `go test ./...` |
| `Gemfile` + rspec | RSpec | `bundle exec rspec` |
| `*.spec.ts`, playwright | Playwright | `npx playwright test` |

Ничего не нашёл — спроси пользователя, каким раннером писать, или предложи
минимальный (для Node — Vitest, для Python — pytest). Не тащи новый фреймворк,
если в проекте уже есть свой.

### Шаг 2. Тест на находку

По каждому CONFIRMED из отчёта напиши тест, повторяющий эксплойт из находки:

- **AC-1** (чужой объект): залогинься как пользователь A, запроси объект
  пользователя B по id — тест ждёт отказ (403/404), не данные.
- **AC-2** (роль только во фронте): дёрни админ-эндпоинт из-под обычной роли —
  тест ждёт отказ.
- **AU-1** (перебор): 6+ попыток входа подряд — тест ждёт блокировку после 5.
- **IN-1** (SQL): подставь `' OR '1'='1` в поле — тест ждёт, что запрос не
  вернул чужие строки.
- **IN-2** (XSS): сохрани `<script>` в поле, запроси страницу — тест ждёт
  экранированный вывод.
- **RL-3** (гонка): пошли N одновременных запросов на списание — тест ждёт одно
  списание, не N.
- **EX-1** (вебхук): пошли вебхук без/с неверной подписью — тест ждёт отказ.
- **EX-2** (CORS): запрос с чужого Origin — тест ждёт, что заголовок не
  разрешает.

Остальные пункты — по критерию закрытия из чеклиста.

Тест кладётся рядом с тестами проекта (или в `tests/security/`), помечается
id пункта в имени: `test_AC-1_order_ownership`.

### Шаг 3. Прогон и отчёт

Прогони набор. Отчёт: пункт → red было / green стало / всё ещё red (не
починено). Всё ещё red — это открытая дыра, не тихо оставляй.

## Зелёный вывод сворачивается сам

Блок ставит хук `quiet-tests`: тестовые команды (jest, vitest, pytest, go test,
rspec, playwright, mocha) он оборачивает в `green-filter`. Зелёный прогон
сворачивается в одну строку, красный печатается целиком. Контекст не забивается
простынёй «PASS PASS PASS».

Работает само, пока блок включён. Версия Codex без поддержки `updatedInput`
не перепишет команду — тогда гоняй тесты руками через обёртку:

```bash
node "путь/hooks/green-filter.js" --b64 $(printf '%s' 'npx jest' | base64)
```

## Недоверие

Не верь, что находка настоящая, пока тест не упал на живом коде. Тест — арбитр
над отчётом аудита. Аудит мог ошибиться, тест это ловит: не упал red — находка
под вопросом, верни её на разбор.

## Границы

- Не чинит код сам без просьбы. Пишет тест, показывает red, ждёт фикс.
- Не поднимает прод. Тесты гоняются на тестовом контуре (OP-3).
