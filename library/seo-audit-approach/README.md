# Подход к техническому SEO-аудиту — советчик по выбору

Не альтернативные блоки — сравнение подходов внутри и вокруг блока
`seo-audit`, до того, как решать, нужен ли живой API-доступ поверх
встроенной промпт-методологии.

## Три подхода в источниках

### seojuice-стиль — промпт-only, без ключей (уже встроен в `seo-audit`)

4-слойная диагностика (crawlability→indexability→renderability→signals),
работает по коду/HTML/доступной странице напрямую — `curl`/`WebFetch`,
без обращения к платным API. Не требует настройки, ключей, MCP-сервера.
Глубина ограничена тем, что видно статически: без Search Console не видно
реальных данных индексации (сколько страниц реально в индексе, ошибки
покрытия за период), без живого краулера — обхода тысяч страниц за один
проход.

**Дефолт codex-kit.** Работает из коробки на любом проекте, не требует
решения «покупать ли API» до первого запуска.

### open-seo — MCP + живые данные (опция для тех, у кого есть API-доступ)

MCP-сервер поверх DataForSEO-подобных данных: реальный краул сайта,
backlinks overview, domain overview, keyword research. Даёт то, что
статический подход не может — фактические данные об индексации, реальный
трафик, конкурентные метрики. Требует ключ/подписку и настройку MCP.
Лицензия репозитория не подтверждена текстом README (см. атрибуцию в
`blocks/seo-audit/block.yaml`) — методология в блоке синтезирована своими
словами, не скопирована дословно.

**Когда ставить**: проект уже платит за DataForSEO/аналог, или нужен
реальный аудит по объёму страниц, который вручную не обойти (крупный
сайт, десятки тысяч URL).

### web-quality-skills — Lighthouse/CrUX-based (другая цель измерения)

Метрики через Lighthouse и полевые данные CrUX, тот же набор Core Web
Vitals, что и `web-fundamentals`/`web-motion` в стеке `interface`. Не
дублирование по случайности — цель измерения другая: там CWV меряют ради
UX, здесь (в `seo-audit`) — ради root-cause сигнала ранжирования. Числа
совпадают, вопрос «зачем чиним» разный. См. также `CONFLICTS.md`, раздел
про стек `seo`.

## Рекомендация

Дефолт — seojuice-стиль, уже встроен в `blocks/seo-audit`. Переходить на
open-seo-подход (MCP + живые данные) только когда у проекта уже есть
API-доступ к SEO-данным или объём страниц не позволяет статический обход
вручную/через `curl`. Не ставить оба сразу как основной инструмент —
дублирование диагностики одного и того же (см. `library/codebase-map`
для аналогичной логики выбора одного основного инструмента).
