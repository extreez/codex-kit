# Принципы: когда экономят, когда становятся ритуалом

Сжато с principles-wiki.net. Не чек-лист для галочки — набор вопросов,
которые стоит держать в голове при решении границы.

## SOLID

- **S (одна причина для изменения)** — экономит, когда модуль реально меняют
  по двум разным поводам от двух разных людей/команд. Не экономит, если
  расщепить класс на пять просто потому что «так положено» — это лишний
  переход между файлами без пользы.
- **O (открыт для расширения, закрыт для изменения)** — экономит там, где
  новые варианты добавляются часто и предсказуемо (новый тип платежа, новый
  формат экспорта). Не стоит городить заранее ради гипотетического расширения,
  которого может не быть — это уже YAGNI из ponytail.
- **L (подстановка Лисков)** — важно там, где реально есть иерархия
  наследования с полиморфным вызовом. Нет наследования — принцип неприменим,
  не нужно его притягивать.
- **I (не заставляй реализовывать лишнее)** — маленькие специфичные интерфейсы
  вместо одного большого. Экономит, когда разные вызывающие используют разные
  подмножества методов.
- **D (зависимость от абстракции)** — оправдана, когда конкретная реализация
  меняется (тестовый дублёр, смена поставщика). Не оправдана для единственной
  реализации, которая никогда не заменится — это интерфейс с одной реализацией,
  запрещённый в ponytail.

## Другие

- **DRY** — про знание, не про текст. Две одинаковые строчки кода, которые
  выражают разные бизнес-правила и меняются по разным причинам, — не
  дублирование, это совпадение. Обобщать их — создать ложную связь.
- **KISS** — при прочих равных выбирать решение с меньшим числом движущихся
  частей. Не довод против необходимой сложности, довод против случайной.
- **GRASP (Low Coupling / High Cohesion)** — модуль зависит от малого числа
  соседей (low coupling) и всё внутри модуля решает одну связную задачу
  (high cohesion). Хороший быстрый тест границы: если модуль трудно объяснить
  одним предложением — вероятно, в нём смешаны две задачи.

## Как применять

Спросить не «нарушен ли принцип формально», а «какой конкретный риск этот
принцип здесь снимает». Нет риска — принцип не даёт пользы, применять не нужно.
