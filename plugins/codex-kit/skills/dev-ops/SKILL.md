## CI/CD

Пайплайн из шагов, каждый — гейт, не украшение: собрать → тесты → линт →
(опционально) деплой на стейджинг. Гейт красный — следующий шаг не идёт.

Не переносить в пайплайн то, что не гейт: форматирование кода — pre-commit
хук на машине разработчика, не отдельный шаг CI, который может провалиться
и заблокировать мердж из-за пробела.

Секреты пайплайна — через переменные окружения CI, не в файле пайплайна.
Если проект уже несёт стек `secure`: тот же принцип, что в `sec-policy`, секрет
в конфиге — та же дыра, что и в коде.

Конкретный гейт для GitHub Actions (порядок джобов, не дословный YAML):
тесты → сборка и push образа с тегом окружения (не `:latest`) → для
инфраструктуры отдельным шагом `terraform plan`, `apply` только если план
показал изменения (см. `deploy-terraform`, если провижининг через
Terraform) → деплой манифестов. Окружение (dev/staging/prod) определять по
ветке, не по ручному вводу — меньше шанс задеплоить не туда веткой.

### GitOps как альтернатива push-деплою

Пайплайн необязательно должен сам применять манифесты в кластер — вариант
GitOps: CI собирает и пушит образ, коммитит новый тег в отдельный
Git-репозиторий манифестов, а деплой в кластер делает контроллер (ArgoCD/
Flux), который следит за этим репозиторием и сам подтягивает изменения.
Плюс — единый аудит-лог (git log = история деплоев) и откат через `git
revert`, а не через доступ к кластеру у CI-раннера. Ставить, когда важна
трассируемость «кто задеплоил что и когда» и не хочется держать
kube-credentials в CI-секретах.

## Решения (ADR)

Architecture Decision Record — короткий файл на одно решение, не на весь
проект. Формат: что решали, какие варианты рассматривали, что выбрали, почему,
чем расплачиваемся за это решение.

Писать ADR только когда решение спорное или дорогое отменить — не на каждый
чих. Тривиальный выбор без ADR, это уже избыточная бюрократия.

Файлы: `docs/decisions/NNNN-короткое-название.md`, нумерация по порядку,
старые не переписывать — новое решение отменяет старое новым файлом со
ссылкой на отменённый.

Формат на одно решение: заголовок, статус (Proposed/Accepted/Rejected/
Superseded/Deprecated), контекст, само решение, последствия отдельно
положительные/отрицательные, рассмотренные альтернативы с причиной отказа от
каждой. Пункты внутри раздела — короткими кодами (`POS-001`, `NEG-001`,
`ALT-001`) для удобной ссылки из других документов, не сплошным текстом.

## История изменений

Хук блока (`changelog-gate.js`, уже активен) при выходе из сессии сверяет
git diff: список зависимостей поменялся, CHANGELOG — нет, напоминает один
раз. Настройки не требует.

Changelog собирается из commit-сообщений, не пишется с нуля. Conventional
commits (`feat:`, `fix:`, `chore:`) на входе — секции Added/Fixed/Changed на
выходе. Коммит без типа — не потерять, положить в отдельную секцию
«Разное», не выкидывать молча.

Одна запись — одна пользовательская польза, не список изменённых файлов.
«Добавлена оплата картой», не «изменён payment.ts».

## Наблюдаемость (база, не мониторинг живого прода)

Здесь — что заложить в код заранее, чтобы потом было что смотреть, не сама
система мониторинга (та — отдельная задача, когда появится живой прод, см.
`NOTES.md` про Incident Commander).

- Структурные логи (объект, не строка): что произошло, где, с каким
  идентификатором запроса — а не человекочитаемая фраза, которую потом не
  распарсить.
- На каждую операцию, которая может тихо сломаться, — явный лог входа/выхода
  с результатом, не полагаться, что ошибка сама всплывёт наверх.
- Не логировать секреты и персональные данные целиком — тот же принцип, что
  в `sec-policy`.
