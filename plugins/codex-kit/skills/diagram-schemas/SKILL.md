# Диаграммы архитектуры и процессов

Диаграмма это не иллюстрация к тексту, а отдельный носитель смысла. Если её
можно молча заменить списком, значит она не нужна: рисовать стоит только то,
что теряется при пересказе словами, связи, порядок, ветвление, границы.

## Роль относительно соседних блоков

Этот блок не сканирует код и не строит граф зависимостей сам, он рисует по
готовому пониманию системы, которое либо уже есть у агента, либо получено из
описания пользователя. Если нужна карта реального репозитория, сначала звать
блок из группы `codebase-map` (`repowise` по умолчанию, `graphify` для
разового HTML-экспорта), и уже его результат превращать в диаграмму здесь.

Если на входе таблица чисел или ряд измерений, это `chart-selection`, не
этот блок. Граница простая: если оси и величины значат больше, чем связи,
это чарт. Если связи и порядок значат больше, чем числа, это диаграмма.

## Шаг 1: выбрать тип по вопросу читателя

| Тип | Отвечает на вопрос |
|---|---|
| `architecture` | Из каких частей состоит система, кто с кем связан, где границы |
| `workflow` | В каком порядке идёт процесс, где развилки и точки согласования |
| `sequence` | Кто кого вызывает по времени, какой ответ приходит и когда |
| `dataflow` | Откуда данные приходят, что их трансформирует, куда попадают |
| `lifecycle` | В каких состояниях бывает объект и что переводит его из одного в другое |

Тип не всегда очевиден из формулировки запроса. Спутанный процесс с
развилками и повторами часто на самом деле `lifecycle` (состояния), а не
`workflow` (шаги) - проверить: если у объекта есть название текущего
статуса ("в ожидании", "отменён", "выполнен"), это `lifecycle`.

## Шаг 2: проверить, не подходит ли готовый семантический паттерн

Прежде чем собирать диаграмму с нуля из примитивов, свериться с
[references/semantic-patterns.md](references/semantic-patterns.md) - семь
именованных паттернов поведения (очередь с узким местом, парные трассы
решений, secure paved road и другие), которые уже решают связку "что
показать" + "какой тип диаграммы ближе всего" + "числовой бюджет сложности"
+ "типичные ошибки". Паттерн отвечает на вопрос "что это за история", тип из
шага 1 отвечает на вопрос "как её разложить по осям страницы" - паттерн не
отменяет тип, а сужает его до конкретной раскладки.

Ни один паттерн не подошёл - не выдумывать десятый, собирать диаграмму
вручную из типа и правил ниже, это тоже нормальный путь.

## Шаг 3: набросать структуру как данные, не как картинку

Прежде чем писать SVG, записать структуру в виде простого списка узлов и
связей. Не обязательно в JSON-файл, можно прямо в рассуждении, но обязательно
до первой координаты:

```
nodes: [{id, label, type, role}]
edges: [{from, to, label, kind}]
```

`type` зависит от выбранного типа диаграммы: для `architecture` это
`frontend / backend / database / cloud / security / external`, для
`lifecycle` это `state` или `terminal`, для `sequence` это `participant`.
`role` это визуальная роль из таблицы обработки узлов ниже
(`focal / backend / store / external / input / optional`), не путать с
`type`, который про предметный смысл узла.

Смысл шага не в формате файла, а в дисциплине: сначала решить, что вообще
есть в диаграмме и как оно связано, потом решать, как это разместить. Прямой
переход к координатам и SVG-разметке без этого списка почти всегда кончается
пересекающимися линиями и связями, добавленными на глаз посреди рисования.

**Бюджет сложности.** Не больше 9 первичных узлов на обзорной диаграмме, не
больше 5 lifelines на sequence-диаграмме. Больше значит либо агрегировать
источники в одну именованную группу ("остальные 12 клиентов"), либо делить
на несколько диаграмм (обзор + деталь), а не сжимать шрифт до нечитаемого.

## Шаг 4: числовые правила разметки

Источник: `diagram-design`, `references/style-guide.md`. Не переизобретать
эти числа на глаз, они уже проверены на разборчивость:

- **Сетка 4px.** Каждая координата, размер и отступ кратны 4. Жёсткое
  правило, не рекомендация.
- **Скругления.** 4px на мелких тегах, 6px на боксах узлов, 8px на
  контейнерах и кольцах.
- **Толщина линий.** 0.8 для тонких контуров листовых узлов, 1 для
  большинства линий, 1.2 для акцентных.
- **Коннекторы.** Скруглённые углы, зазор между стрелкой и подписью 6-10px,
  никаких диагональных линий, только горизонталь/вертикаль со скруглением на
  повороте.
- **Один акцент.** Ровно один цвет для "это здесь главное" (`accent`) на
  диаграмму, не два. Остальное - нейтральные роли ниже.

## Шаг 5: визуальная роль узла определяет заливку/обводку, не выдумывать на глаз

| Роль | Когда применять | Заливка | Обводка |
|---|---|---|---|
| `focal` (1-2 узла максимум) | То, ради чего рисуется диаграмма | акцент, приглушённый | акцент, полный |
| `backend` | Обычный компонент/шаг | нейтральный светлый | базовый контур |
| `store` | Хранилище данных, БД, очередь | нейтральный, чуть темнее фона | приглушённый контур |
| `external` | Внешняя система, вне контроля проекта | почти прозрачный | контур с низкой непрозрачностью |
| `input` | Точка входа, триггер | лёгкая заливка приглушённым | мягкий контур |
| `optional` | Необязательный путь, будущая работа | почти прозрачный | пунктир |

Конкретные HEX-значения этот блок не диктует, они приходят из цветовой
системы проекта. Если системы нет, сгенерировать её через `web-color`
(нейтральная рампа + одна акцентная), не изобретать разовую палитру под одну
диаграмму. Правило контраста то же, что у `web-color`: пара `ink`/`paper`
обязана проходить WCAG AA, не прикидывать на глаз.

## Шаг 6: выбрать конкретный визуальный подтип

Куратор-список самых ходовых подтипов на каждую категорию, с антипаттерном
на каждый - [references/types.md](references/types.md). Список не полный:
у `diagram-design` их 39, здесь собраны самые частые. Если нужный подтип не
в списке, назвать его словами ("нужна matrix-раскладка сравнения ролей") и
собрать по правилам шагов 3-5 без готового рецепта, это не ошибка.

## Шаг 7: самопроверка перед выдачей

Пройти [references/self-check.md](references/self-check.md) до того, как
показать результат пользователю. Список коротких да/нет проверок, не
судейское ревью с оттенками. Не прошло - почистить и прогнать снова, не
называть проваленный пункт нормой.

## Формат вывода

Один самодостаточный HTML-файл со встроенным SVG, без внешних зависимостей
кроме шрифтов через `<link>` (если тема проекта их уже использует). Тёмная
и светлая тема через тот же порядок токенов, что в `artifact-design`:
`:root` даёт светлые значения, `@media (prefers-color-scheme: dark)`
переопределяет их, `[data-theme]` перебивает оба явным выбором пользователя.
Не выдумывать собственный порядок приоритета токенов, использовать этот.

Если диаграмма рисуется как один SVG-блок внутри уже существующего
артефакта (не отдельным файлом) - механика инлайн-SVG (viewBox, вёрстка
внутри артефакта, читаемость в обеих темах) это зона встроенного скилла
`artifact-diagramming`, читать его для этого случая. Этот блок не
переопределяет его механику отрисовки, а добавляет то, чего там нет:
типизированный черновик перед рендером, числовой style-guide (шаг 4-5) и
семантические паттерны - они применимы в обоих случаях, отдельный файл или
блок внутри артефакта.
