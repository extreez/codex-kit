# Семантические паттерны

> Источник: cathrynlavery/diagram-design, `references/semantic-patterns.md`,
> MIT, дословный перевод с сохранением структуры и числовых бюджетов.

Семантический паттерн описывает, что делает система. Визуальный тип из
`references/types.md` описывает, как разложить информацию по странице.
Сначала выбирается паттерн, если поведение, состояние, контроль или риск
важнее самой раскладки, потом - ближайший визуальный тип как раскладка для
этого паттерна. Ни один паттерн не подошёл - выбирается тип напрямую.

Один основной паттерн на рисунок. Второй паттерн может дать не больше одного
вспомогательного примитива; если оба претендуют на полноценное место, значит
рисунков должно быть два: обзорный и детальный.

## Таблица маршрутизации

| Читателю нужно понять... | Паттерн | Ближайший тип |
|---|---|---|
| Много заявок конкурируют за ограниченную мощность обслуживания | Очередь с узким местом | Data flow |
| Одни и те же вопросы/входы/контроли/выходы повторяются на разных стадиях | Каркас стадий с семантическими слотами | Process |
| Разговор без структуры становится устойчивой структурированной записью | Неструктурированный вход → структурированный артефакт | Data flow |
| Почему два похожих решения разошлись и в какой точке | Парные трассы оценки политики | Flowchart |
| Какие маршруты пересекают границу доверия, а какие заблокированы | Secure paved road | Architecture |
| Какие контроли применяются на каждой точке принуждения | Каталог контролей/governance | Layer stack |
| Как защитные слои снижают риск и что остаётся | Компенсирующие слои безопасности | Layer stack |

## 1. Очередь с узким местом

**Когда выбирать:** несколько источников сходятся к одному ревьюеру, сервису,
шлюзу или ограниченному ресурсу; важны темп прибытия, глубина очереди,
ожидание, мощность, backpressure.

**Обязательные элементы:** отдельные источники; сведённый вход; упорядоченная
очередь с видимыми слотами и счётчиком; подпись мощности/темпа обслуживания;
одна точка узкого места; исходы "принято" и "отложено/отклонено". Подписывать
единицами измерения ("8/час", "3 слота"), не словом "много".

**Бюджет сложности:** ≤5 источников, ≤5 слотов очереди, одно узкое место, два
исхода, ≤9 первичных узлов. Избыточные источники агрегировать в именованную
когорту.

**Антипаттерны:** конвейер равной ширины, скрывающий давление; стрелки,
слитые до точки, где их нельзя проследить; мощность, показанная только
размером бокса; декоративное скопление; анимация, меняющая порядок элементов;
один только красный цвет как признак перегрузки.

**Ближайший тип:** Data flow по умолчанию; Process, если важнее стадии
обслуживания, а не источники.

## 2. Каркас стадий с семантическими слотами

**Когда выбирать:** жизненный цикл или операционная модель повторяет одни и
те же семантические вопросы на разных стадиях (обычно Вопрос, Вход,
Контроль, Выход). Важнее сравнимость между стадиями, чем порядок сообщений
во времени.

**Обязательные элементы:** упорядоченные заголовки стадий; согласованная
сетка слотов; явные пустые/неприменимые слоты; передача между стадиями;
устойчивые подписи слотов; один основной выход на стадию. Порядок слотов
сохраняется на каждой стадии.

**Бюджет сложности:** 3-6 стадий, 3-4 вида слотов, ≤20 заполненных ячеек,
≤2 строки текста на ячейку. Деталь, требующая прозы, выносится отдельно.

**Антипаттерны:** каждая стадия придумывает свою внутреннюю раскладку;
значение слота кодируется только позицией без подписи; ложная точность из
десятков ячеек; смешение порядка стадий с дорожками владельцев; уменьшение
текста ради одного холста.

**Ближайший тип:** Process; Swimlane только если повторяющиеся строки это
владельцы, а не семантические слоты.

## 3. Неструктурированный вход → структурированный артефакт

**Когда выбирать:** диалог, заметки, запрос без структуры извлекаются,
нормализуются и записываются в устойчивый бриф, тикет, запись, схему или
другой структурированный артефакт.

**Обязательные элементы:** исходные реплики; уточняющие вопросы; извлечённые
пары поле/значение; названное преобразование; граница устойчивого артефакта;
связи происхождения от конкретных реплик к полям; состояние
неизвестно/пропущено.

**Бюджет сложности:** ≤4 реплики, ≤6 полей артефакта, одно преобразование,
≤3 связи происхождения. Показывать характерное содержание, не полную
стенограмму.

**Антипаттерны:** "магия ИИ" искрой между двумя боксами; артефакт показан как
ещё один пузырь чата; поля появляются без источника; выдуманная уверенность
для отсутствующих фактов; анимация печати как единственный читаемый текст.

**Ближайший тип:** Data flow; Process, если извлечение проходит через
несколько упорядоченных проверок.

## 4. Парные трассы оценки политики

**Когда выбирать:** два похожих запроса приходят к разным исходам; читателю
нужен статус `PASS`/`FAIL`/`SKIPPED`/`NOT REACHED` по каждому правилу и
точка первого расхождения.

**Обязательные элементы:** одни и те же упорядоченные правила на обеих
трассах; явный текст статуса плюс символ/форма; различающиеся входы;
финальные исходы; подписанный маркер первого расхождения; различие между
`SKIPPED` (применимый путь намеренно пропущен) и `NOT REACHED` (оценка
остановилась раньше).

**Бюджет сложности:** ровно 2 трассы, 3-6 правил, одно первое расхождение,
≤12 ячеек статуса, один исход на трассу. Текст правила длиннее одной строки
выносится в заметки.

**Антипаттерны:** сравнение двух независимо упорядоченных потоков;
зелёные/красные точки без слов; смешение "пропущено" и "не достигнуто";
подсветка каждого различия; продолжение отклонённой трассы так, будто
дальнейшие правила выполнялись.

**Ближайший тип:** Flowchart для упорядоченной логики решений; Sequence
только если сообщения между акторами и время тоже важны.

## 5. Secure paved road

**Когда выбирать:** поддерживаемая архитектура создаёт ограниченный маршрут
от сборки до деплоя; важны границы доверия, привилегированные точки,
разрешённый и запрещённый вход, одобренный и заблокированный путь деплоя.

**Обязательные элементы:** подписанные границы доверия; акторы и identity;
разрешённый вход с положительной текстовой подписью; запрещённый вход,
обрывающийся на границе; одобренный путь деплоя; заблокированный обходной
путь; привилегированный шлюз; изолированный runtime; точка аудита.
Использовать разный стиль линии и разные символы остановки, не только цвет.

**Бюджет сложности:** ≤3 зоны доверия, ≤8 компонентов, ≤10 путей, ≤2
запрещённых пути, один привилегированный шлюз. Каталог контролей выносится
отдельным рисунком.

**Антипаттерны:** пунктирный бокс "безопасность" без семантики маршрута;
запрещённая стрелка, всё же пересекающая защищённую зону; секреты или
identity подразумеваются, но не подписаны; каждый компонент стилизован как
доверенный; обходной путь визуально снова сливается с одобренным.

**Ближайший тип:** Architecture.

## 6. Каталог контролей / governance

**Когда выбирать:** реестр контролей нужно понимать по точке принуждения:
авторинг, workspace, merge/CI, деплой/runtime или другая именованная
поверхность. Обычный чек-лист скрыл бы эти точки.

**Обязательные элементы:** группы по поверхности принуждения; названные
контроли; актор принуждения (`код`, `платформа`, `человек`); момент
(`запись`, `merge`, `деплой`, `запуск`); возможность обхода или маршрут
исключения; отметка покрытия/пробела.

**Бюджет сложности:** 3-5 поверхностей, 3-7 контролей на поверхность, ≤24
контроля всего, ≤3 атрибута на контроль. Числа суммировать только если
список уже есть в другом месте.

**Антипаттерны:** 35 мелких таблеток; группировка по расплывчатым темам
вместо точки принуждения; смешение желаемого с реально применяемым; иконки
без названия контроля; заявление о defense-in-depth без показа покрытия по
поверхностям.

**Ближайший тип:** Layer stack; DP security matrix, если важнее сравнение
прав ролей, а не поверхности принуждения.

## 7. Компенсирующие слои безопасности

**Когда выбирать:** ни один слой не идеален; каждая защита закрывает то, что
пропустил предыдущий слой, и остаточный риск должен видимо сужаться,
передаваться или оставаться через весь стек.

**Обязательные элементы:** упорядоченный вход риска/угрозы; названные
защитные слои; митигация каждого слоя; явное ограничение или "утечка";
носитель остаточного риска между слоями; финальный остаточный риск и
последствие/реакция. Обозначать подписями или убывающими величинами,
никогда только площадью фигуры.

**Бюджет сложности:** 3-5 слоёв, одна основная нить риска, ≤2 митигации на
слой, одно финальное утверждение об остаточном риске. Несколько несвязанных
угроз разносятся по отдельным рисункам.

**Антипаттерны:** намёк, что финальный слой обнуляет риск; равные
непрозрачные слэбы без передачи риска; аудит как предотвращение; уменьшение
фигур без числового или словесного смысла; смена порядка
предотвращение/обнаружение/восстановление без объяснения.

**Ближайший тип:** Layer stack; Nested, если важнее границы вложенности, а
не порядок компенсации.

## Правила композиции

- Семантический паттерн может специализировать примитивы статуса, границы,
  очереди или распространения; выбранный тип по-прежнему владеет осью
  страницы, грамматикой коннекторов, отступами и лимитами конкретного типа.
- Применяется более строгий из двух бюджетов - паттерна и визуального типа.
  Ячейки/статусы паттерна не дают права превысить лимит в девять узлов на
  обзорной диаграмме.
