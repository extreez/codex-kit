# Документ дизайн-системы: создать и контролировать

Одна задача, не две отдельных — по прямому решению пользователя `create`
и `control` не разносятся по разным блокам/скиллам. Ниже оба режима
одного и того же скилла, из двух источников с одинаковой идеей "файл —
источник истины, инструмент сверяет факт с ним".

## Режим 1 — создать: hallmark study (извлечь ДНК)

Не копирование пикселей. Пять слоёв извлечения: Surface (цвет/оттенок/
footprint), Type (роли шрифтов, в режиме URL — точные названия из
`@font-face`/Google Fonts/`next/font`), Structure (сопоставление с
макроструктурами и архетипами компонентов), Motion (библиотеки анимации,
паттерны reveal, антипаттерны вроде `transition: all`), Rhythm (плотность/
асимметрия — недоступно в режиме URL, помечается `unknown (URL mode)`).

Полный протокол (включая полную защиту от SSRF — конкретные CIDR-
диапазоны для внутренних/приватных адресов, проверку редиректов, трактовку
prompt injection из чужого HTML как враждебных данных) —
[study.md](study.md), дословно на английском.

Результат при желании фиксируется в `design.md` — с этого момента файл
читается в первую очередь, и правило diversification (не повторять
архетип) инвертируется в consistency: дальнейшая генерация обязана
сверяться с зафиксированным.

## Режим 2 — зафиксировать контракт: tastemaker style-lock.md

`.tastemaker/style-lock.md` — единственный источник истины по визуальному
стилю проекта, как только он установлен. Все последующие запросы читают
токены отсюда, не переизобретают.

Полный формат — [style-lock-format.md](style-lock-format.md), дословно на
английском. Ключевое: **color contract** — не пять hex-значений, а
таблица обязательных коэффициентов контраста по типу пары (текст на фоне
`4.5:1`, лейбл кнопки на заливке `4.5:1`, заливка UI-компонента на
странице `3:1`, декоративная граница — без требования), с командой
проверки `scripts/check_contrast.py --matrix ...` и раскладкой результата
на три легальных списка (Text-safe / UI-safe / Decorative) — модель может
комбинировать цвета только из них. Плюс типографика, форма, плотность
(шкала 4px), структура страницы, лог решений (`.tastemaker/decisions.log`)
и секция **"Do not"** — конкретные запреты именно этого проекта.

## Режим 3 — контролировать: tastemaker audit (обнаружить дрейф)

Не редактирует — только сверяет. Читает существующий UI (файл/директория/
URL/скриншот) против чек-листа находок и, что важнее для дрейфа, против
CSS-комментария-stamp вида `/* tastemaker · macrostructure: <name> · ...
*/`, который сам код должен нести. Несовпадение заявленного в stamp с тем,
что реально на странице — `critical: stamp lies`. Это и есть механизм
контроля: `style-lock.md` фиксирует контракт, `audit` — сверяет факт с
ним, не полагаясь на честное слово.

Полный текст — [audit.md](audit.md), дословно на английском.

## Соседние блоки

`design-system-tokens` — архитектура примитив→семантика→компонент,
структурирует то, что `style-lock.md` держит как контракт по ролям.
`figma-canvas/design-docs` (`design-system-documentation`) — та же роль
документации, но исполнение внутри Figma. `web-taste/gate-check` — тоже
контроль, но универсальный anti-slop гейт, не привязанный к
project-specific контракту конкретной дизайн-системы.

## Проверяемый результат (для /loop-build)

Есть готовый инструмент дрейфа: `tastemaker/verbs/audit.md` сверяет
CSS-stamp (контракт `style-lock`) с реальной страницей. Готово — когда
`audit` не находит расхождений между зафиксированным контрактом и тем,
что реально в CSS. Сам `study.md` (извлечение ДНК) не проверяем командой —
это разовое суждение о референсе, не то, что зацикливается.

## Несколько поверхностей сразу — распараллелить

Контракт (`style-lock`) уже зафиксирован, нужно свести к нему много
страниц/компонентов сразу — subagent на страницу, каждый гонит свой
`audit` против общего контракта (контракт читают, не пишут — гонки нет).
Сам контракт из референса выводится один раз, не параллельно — иначе
получишь N разных прочтений одного референса вместо одного контракта.
