# seo-audit

Технический аудит по 4 слоям, снизу вверх: страницу, которую не может
обойти краулер, бессмысленно проверять на структурированные данные.

## Шаг 0. Что на входе

Спроси, если не сказано: URL или локальный проект, доступ ли есть к
`robots.txt`/`sitemap.xml`/Search Console, публичный сайт или staging
за паролем (краулер тогда не дойдёт — работай по исходникам). Без этого
контекста аудит превращается в угадывание.

## 4 слоя диагностики

Проверяй по порядку. Находка на нижнем слое (например, страница закрыта
`robots.txt`) обесценивает проверки более высоких слоёв для этой же
страницы — сначала укажи блокер, остальное по ней помечай «не проверено
из-за блокера выше».

### Слой 1. Crawlability — доходит ли краулер до страницы

- `robots.txt` существует, не блокирует нужные разделы, не блокирует
  CSS/JS, нужные для рендера.
- `sitemap.xml` существует, указан в `robots.txt`, валиден (не превышает
  50k URL / 50Мб на файл), URL в нём отдают 200, не редиректят.
- Внутренняя перелинковка: страница достижима за ≤3 клика с главной, нет
  «сиротских» страниц (есть в sitemap, но нет входящих внутренних ссылок).
- Цепочки редиректов короче 3 прыжков, нет циклов, нет 404 в цепочке.
- Глубина краула не убита пагинацией без `rel=next/prev` или бесконечным
  скроллом без serverside-фолбэка.

### Слой 2. Indexability — может ли страница попасть в индекс

- `<meta name="robots">` и HTTP-заголовок `X-Robots-Tag` не содержат
  `noindex` там, где страница должна индексироваться (и наоборот — сверить,
  что закрыты дубли/служебные страницы).
- Канонический тег `<link rel="canonical">` указывает на себя или на
  предпочтительную версию, не создаёт цепочку канониклов, не расходится
  с sitemap.
- Дубли контента: параметризованные URL (`?sort=`, `?utm_=`), версии
  http/https, www/non-www, с/без слэша — сведены к одному канониклу.
- `hreflang` (если сайт мультиязычный):
  - взаимные ссылки: если страница A ссылается на B через `hreflang`, B
    обязана ссылаться обратно на A (одностороннюю связь поисковик
    игнорирует целиком).
  - self-referencing: страница указывает `hreflang` на саму себя в списке
    альтернатив, не только на другие версии.
  - `x-default` задан там, где есть версия без привязки к языку/региону
    (страница выбора языка, международный лендинг) - без него поисковик
    сам гадает, какую версию показывать пользователям вне заданных языков.
  - нет расхождения с canonical: `hreflang` и `canonical` не указывают на
    разные URL для одной и той же языковой версии.
- Пагинация проиндексирована осмысленно — не 40 одинаковых по контенту
  `?page=N` без уникального сигнала.

### Слой 3. Renderability — видит ли краулер контент так же, как человек

- Определи рендер: SSR/SSG (html из curl совпадает с DOM) или CSR
  (контент подгружается JS). Для CSR — проверь, что критичный для SEO
  контент (заголовки, основной текст, ссылки) есть в исходном HTML или в
  снапшоте после рендера (Google рендерит, но со сдвигом по времени —
  бюджет краула не бесконечный).
- Ключевые ссылки — настоящие `<a href>`, не `onclick`/`div` без href
  (краулер такие не проходит).
- Ленивая загрузка изображений и контента ниже фолда — с
  `loading="lazy"` и без блокировки индексации остального текста.
- Render-blocking ресурсы (синхронный JS/CSS в `<head>`) не откладывают
  появление основного контента дольше пары секунд.

### Слой 4. Signals — что видит и как оценивает страницу

- **Title**: уникален по сайту, 50-60 символов, ключевая сущность ближе
  к началу, не дублирует title других страниц.
- **Meta description**: уникально, 140-160 символов, не keyword stuffing.
- **Заголовки H1-H6**: один H1 на страницу, иерархия без пропуска уровней,
  заголовки отражают структуру контента, не декоративны.
- **Structured data (Schema.org)**: валиден (проверить через тестер
  разметки), тип разметки соответствует контенту, нет разметки на
  невидимый пользователю контент (нарушение правил). Обязательные поля и
  частые ошибки по типам:

  | Тип | Обязательные поля | Частая ошибка |
  |---|---|---|
  | Article | `headline`, `datePublished`, `author`, `image` | `datePublished` не совпадает с реальной датой на странице |
  | Product | `name`, `image`, `offers` (с `price` и `priceCurrency`) | `offers` без актуальной цены/наличия - устаревшие данные хуже отсутствия разметки |
  | LocalBusiness | `name`, `address`, `telephone` | адрес в разметке расходится с NAP на странице контактов (см. `seo-local`) |
  | FAQ | `mainEntity` с парами `Question`/`acceptedAnswer` | вопрос-ответ не совпадает с видимым текстом страницы (разметка на скрытый контент) |
  | HowTo | `step` (упорядоченный список), `name` | шаги в разметке не совпадают по порядку с шагами на странице |
- **Core Web Vitals — root-cause, не только цифра**: LCP (что именно
  элемент — картинка/текст/видео, что его задерживает — сервер, ресурс,
  рендер), CLS (какой элемент двигается — реклама/шрифт/картинка без
  size), INP (какой обработчик долго блокирует поток). Считать полезным
  находку только с указанием причины, «LCP плохой» без причины — не
  находка, а измерение.
- **Изображения**: `alt`-текст на контентных изображениях (не декоративных
  — у тех `alt=""` осознанно), формат/сжатие не раздувает вес страницы.
- **Внутренняя перелинковка signals**: анкоры релевантны целевой странице,
  не только «читать дальше» на всех ссылках.

Подробный проверяемый чеклист с критериями закрытия — `references/checklist.md`.

## Воркфлоу (9 шагов, гейты обязательны)

1. **Контекст.** Прочитай, что уже известно о сайте (тип, стек, есть ли
   прошлый отчёт этого скилла — `docs/seo/audit-*.md`). Без контекста
   аудит стартует вслепую — гейт: не начинай слой 4, пока не прошёл 1-3.
2. **Детект стека.** Статический сайт / SSR-фреймворк (Next/Nuxt/Astro) /
   CSR-SPA / CMS (WordPress и т.п.) — фокусирует, что смотреть в слое 3.
3. **Слой 1: Crawlability.** `robots.txt`, `sitemap.xml`, внутренняя
   перелинковка, редиректы.
4. **Слой 2: Indexability.** Meta robots, canonical, дубли, hreflang.
5. **Слой 3: Renderability.** SSR/CSR, ссылки как `<a>`, render-blocking.
6. **Слой 4: Signals.** Title/description/headings/schema/CWV root-cause/
   alt/перелинковка.
7. **Гейт на количество находок.** Не больше 5-10 находок в отчёте за
   проход. Если проблем больше — бери самые severity-критичные (блокеры
   индексации > дубли > сигналы), остальные — в раздел «дальше по списку»
   без утопления отчёта в мелочи. Это гейт из open-seo: отчёт на 40
   находок никто не прочитает и не починит.
8. **Lighthouse/полевые метрики — по умолчанию выключены.** Не гоняй
   автоматический аудит производительности как часть этого скилла (это
   зона `web-fundamentals`) — здесь CWV разбирается только как SEO-сигнал
   ранжирования, root-cause без запуска инструментов. Включай отдельным
   шагом только если пользователь просит именно замер, не диагностику.
9. **Отчёт.** См. формат ниже.

## Формат отчёта

Два раздела как в `sec-audit` (по образцу — конкретика вместо общих слов):

**Находки** (максимум 5-10, отсортированы по severity):
- severity (blocker / high / medium / low)
- слой (1-4)
- URL и элемент («заголовок `<title>` главной страницы», «строка 14
  `sitemap.xml`»)
- что не так и почему это мешает ранжированию/индексации
- как исправить (конкретно, не «улучшить SEO»)

**Не проверено**: разделы сайта без доступа, слои, недостижимые из-за
блокера выше, инструменты, которых не было (Search Console, живой краулер).
Молчать о пропусках нельзя — иначе отчёт читается как «всё чисто».

Сохраняй в `docs/seo/audit-<дата>.md` (или куда скажет пользователь).

## Границы

- Аудит не чинит код и не переписывает контент. Только находит и
  объясняет.
- Не бьёт по живым API (DataForSEO/SerpApi) по умолчанию — сравнение
  подхода с API-версией см. `library/seo-audit-approach/README.md`.
