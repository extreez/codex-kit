# paid-ads-loop

Автоматизирует `paid-ads` двумя механизмами: гейт на выходе из сессии,
цикл readback-решение. По образцу `seo-loop`, адаптировано под
жизненный цикл рекламного теста — триггер здесь не изменённый файл
(как в SEO), а истёкшая по времени дата планового окончания теста.

## Формат трекера

`docs/marketing/paid-ads-tests.md`:

```markdown
| Тест | Платформа | Начало | Плановое окончание | Решение |
|---|---|---|---|---|
| Новый hero-креатив | Meta | 2026-08-20 | 2026-09-03 | |
```

Колонка «Решение» заполняется после readback: `promote`, `rollback` или
`extend` (нужно больше данных — новое плановое окончание в колонке
«Плановое окончание», строка не считается зависшей).

## 1. Stop-гейт (хук, уже активен блоком)

Хук `stop-gate.js` парсит `docs/marketing/paid-ads-tests.md` (если файла
нет — не мешает) и блокирует конец сессии один раз, если находит строку
с датой планового окончания в прошлом и пустой колонкой «Решение».
Дата, не diff файлов — рекламная кампания не файл в репозитории, триггер
временной, не по изменению кода.

## 2. Цикл readback-решение

Крутит проход, пока критерий не выполнен: ни одного истёкшего теста без
решения в трекере.

Один проход:
1. Прочитать трекер.
2. Для каждого истёкшего теста — `metrics/analytics-readback`.
3. Записать решение (promote/rollback/extend) в трекер и
   `docs/marketing/readback-log.md`.
4. Повторить.

Собирается через `/goal` и/или `/loop` (скилл `loop-build`) — здесь
особенно уместен `/loop` с интервалом (например раз в день), потому что
триггер временной: тест физически не может закончиться раньше
запланированной даты, ждать событие внутри одной сессии бессмысленно.

Модель и эффорт под каждый шаг спрашиваются при запуске (правило).

## Границы

- Цикл не меняет реальный бюджет/не запускает креативы сам — готовит
  решение, применяет владелец после подтверждения.
- Гейт только напоминает, не блокирует навсегда.
- Не путать с `cro-funnel-loop` (диагностика воронки) и `content-loop`
  (контентный конвейер) — разные объекты цикла.
