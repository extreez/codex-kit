# readme-polish

Не про содержание документации (это `dev-ops`, раздел про решения/историю) —
про то, в каком порядке и какой форме читатель видит README первым делом.

## Диагноз перед правкой

Открой README как первый посетитель, не как автор. Частая болезнь: сначала
внутренние термины проекта, команды установки и дерево директорий — и только
потом, если долистать, ради чего проект вообще существует. Порядок должен
быть обратным.

## Порядок

### Шаг 1. Определить, что проект есть на самом деле

Не с чужого шаблона — из содержания проекта: что делает, для кого, чем
отличается. Без этого любое оформление будет обёрткой без смысла внутри.

### Шаг 2. Порядок чтения

Сверху: одна строка что это и для кого, потом лаконичное доказательство
(скриншот живого результата, короткий пример, счётчик использования — что
реально есть), только потом — установка и техническая часть.

### Шаг 3. Визуальная иерархия

SVG для заголовков/шапки — не растровые картинки, лёгкие и editable. Markdown
для содержания, которое ищется поиском. GIF только если показывает движение,
которое статикой не объяснить — и не как замена тексту.

Бейджи и графики (звёзды, версия, статус, коммиты) — не рисовать вручную,
блок `readme-badges` (CLI shieldcn) сам сканирует стек и выдаёт markdown.

### Шаг 4. Не городить шаблон поверх чужого проекта

Стиль выводится из содержания и назначения конкретного проекта, не копируется
типовой набор бейджиков и разделов из другого репозитория.

### Шаг 5. Поддерживаемость

Разделять по слоям: SVG — визуальная идентичность, Markdown — то, что ищут
текстом. Не встраивать текст картинкой — его потом никто не найдёт поиском
и не обновит.

## Режимы

- **Полная переверстка** — меняется порядок разделов и добавляются
  визуальные элементы.
- **Точечно** — только шапка/иконки разделов, остальной текст не трогается.
  Спросить, какой режим нужен, если из запроса не ясно.

## Соседи

Технически описать архитектуру решения — `dev-ops` (раздел ADR). Не про
внешний вид, а про то, что проект вообще делает и кому подходит — уже решено
раньше, `dev-strategize`.
