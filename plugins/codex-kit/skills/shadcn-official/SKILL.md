# shadcn/ui (официальный)

Не npm-библиотека — компоненты копируются в код проекта командой, а не
подтягиваются рантайм-зависимостью. Правки живут прямо в проекте, апстрим
не привязывает тебя версией пакета. Из-за этого нет смысла ставить как есть
и не трогать — компонент осознанно редактируется после вставки, это его
рабочий режим, не отступление от блока.

## Инициализация проекта

```bash
npx shadcn@latest init -t <framework>
```

`<framework>`: `next`, `vite`, `react-router`, `astro`, `start` (TanStack
Start), также поддерживаются Laravel и Remix — полный список во
флаге `--help`. Создаёт `components.json` (конфиг: алиасы путей, стиль,
базовый цвет, CSS-переменные vs utility-классы) и `lib/utils.ts`.

## Добавление компонента

```bash
npx shadcn@latest add <component>
npx shadcn@latest add button dialog card   # несколько за раз
```

Копирует исходник компонента в путь из `components.json` (обычно
`components/ui/`). Дальше это код проекта — правится напрямую, без
патчей/оверрайдов поверх пакета.

## Skills — контекст о проекте для агента

Отдельный официальный скилл (не CLI, не MCP), ставится тем же
установщиком, что `oklch-skill`/`taste-skill`:

```bash
npx skills add shadcn/ui
```

Разово при загрузке скилл сам запускает `shadcn info --json` и читает
конфигурацию проекта — фреймворк, версию Tailwind, алиасы путей, базовую
библиотеку, библиотеку иконок, уже установленные компоненты. Дальше держит
под рукой полный справочник CLI-команд (`init`, `add`, `search`, `view`,
`docs`, `diff`, `info`, `build`), знание про theming (CSS-переменные) и про
авторство собственных реестров. Даёт агенту собирать составные вещи
("Add a login form with email and password fields", "Build a dashboard with
sidebar and data table"), а не по одному компоненту командой.

Легковесная надстройка поверх CLI, не MCP — тот же принцип "явный вызов
дешевле фонового сервера", что и в разделе выше. Ставить вместе с CLI, не
вместо него.

## MCP сознательно не подключаем

У shadcn есть официальный MCP (`npx shadcn@latest mcp`) — добавление
компонентов диалогом вместо команды. Этот блок его не ставит: MCP-сервер
висит фоновым процессом и ест контекст на каждый вызов, а CLI выше
покрывает ровно то же самое одной явной командой, дешевле и без постоянно
висящего инструмента. Тот же выбор, что у `dembrandt-color` в `web-color`
— явный вызов вместо фонового MCP.

## Тема и токены

`components.json` задаёт базовый цвет и режим (`cssVariables: true/false`).
При `cssVariables: true` тема живёт в CSS custom properties — то самое
место, где встречается `web-color`: примитивы/семантика из `better-colors`
подставляются вместо дефолтной shadcn-палитры, а не сосуществуют рядом с
ней как второй набор токенов.

## Иконки не отсюда

shadcn не поставляет свой набор иконок как часть блока — де-факто дефолт в
шаблонах `lucide-react`, но это соглашение примеров, не требование CLI.
Поиск/подключение иконок через `icons0.dev` — отдельный блок (`icons0-dev`),
не путать с этим.

## Соседние блоки

`shadcn-community` — дополнения и форки поверх этой базы, отдельный реестр
через `components.json`, не смешивать с этим блоком. `web-color` — токены
темы. `web-fundamentals`/`web-taste` — ревью того, что получилось после
вставки компонента, shadcn сам не проверяет качество кастомизации.

## Проверяемый результат (для /loop-build)

Готово — когда `npx shadcn add <component>` завершился без ошибки и файл
компонента появился в `components/ui/`. Реальный exit-код CLI, не мнение.
Качество кастомизации после вставки — уже `web-taste`/`web-fundamentals`,
не этот блок.

## Несколько компонентов сразу — распараллелить

`npx shadcn add button dialog dropdown-menu` — CLI уже ставит пачкой за
один вызов, agent-параллелизация не нужна. Нужна параллельно ещё и
последующая кастомизация каждого под проект — subagent на компонент для
этой части, не для самой установки.
